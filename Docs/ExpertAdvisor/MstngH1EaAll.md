## 1. 目的と範囲

1つのH1チャートにEAを設置し、28通貨のH1判定・発注・SL管理・DB保存・再起動復元を実行する。チャートの通貨はイベントの入口であり、売買対象を限定しない。

既存のH1戦略を各通貨で独立して動かす。複数通貨をまとめた新しいエントリー条件は追加しない。H1共通条件、Spread 5.0 pips以下、初期SL、最大初期SL幅、ZigZagトレイル、Judge成立回数の消費順序を維持する。

以下では、28通貨固定以外を推奨設計として記載する。実装・実運用確認済みの仕様とは区別する。

## 2. 対象通貨と設定

M5観測が利用する`SymbolNameInfoAll.setAll()`を共通の定義元とし、EA独自の28通貨配列を重複定義しない。

```text
USDJPY EURJPY GBPJPY AUDJPY NZDJPY CADJPY CHFJPY
EURUSD GBPUSD AUDUSD NZDUSD USDCAD USDCHF
EURGBP GBPAUD GBPNZD GBPCAD GBPCHF
EURAUD EURNZD EURCAD EURCHF
AUDNZD AUDCAD AUDCHF
NZDCAD NZDCHF
CADCHF
```

| 設定 | 初版案 |
|---|---|
| 対象通貨 | 上記28通貨固定。選択inputなし |
| チャート時間足 | H1 |
| 分析時間足 | 各通貨のMN1・W1・D1・H4・H1 |
| 固定ロット | 現行の`InpLotSize`を全通貨へ適用。既定0.01 |
| 最大初期SL幅 | 現行の`InpMaxInitialStopLossPips`を全通貨へ適用。既定100.0 pips |
| テスター売買開始日時 | 現行の`InpTesterTradeStartTime`を全通貨へ適用 |
| 口座形式 | 現行どおりヘッジ口座 |
| ポジション上限 | 通貨・Magicごとに1。発注中も重複発注を禁止 |
| 通貨別のロット・SL設定 | 初版対象外 |

銘柄名は現在のM5観測と同じ実名を使用する。存在しない銘柄を自動除外したり、似た銘柄へ自動置換したりしない。接頭辞・接尾辞対応が必要な口座は、別途明示的な対応表を設計する。

全体の保有上限はバックテスト結果から決める。最初は全体上限なし・通貨ごとに1ポジション（最大28）で基準テストを行い、同時保有数の分布、損益、ドローダウン、SLまでの損失見込額、証拠金使用、通貨集中を確認する。その後、全体上限の入力（0＝制限なし）と発注待ちを含む枠管理・見送り理由の記録を追加し、候補上限ごとに再テストする。同時成立時の採用順を固定して記録し、別期間でも検証する。観測された最大同時保有数を自動的に運用上限にはしない。

## 3. クラス構成

```text
MstngH1EaAll.mq5
  └─ H1EaMultiSymbolController（全体管理）
       ├─ 28通貨の登録・初期化・終了
       ├─ 1本のTimerと巡回スケジュール
       ├─ 全通貨の保護処理を優先
       ├─ TradeTransactionの振り分け
       └─ H1EaController × 28（通貨ごとの管理）
            ├─ H1EaConfig / MarketContext
            ├─ H1EaStrategy / ElliotAll / HandlePool
            ├─ H1EaEntryState / SignalCount
            ├─ H1EaTradeExecutor / pending SL
            └─ Persistence / Run / Lock / Lease / Logger
```

`H1EaController`を通貨ごとの実行単位として再利用する。戦略・発注ロジックを28通貨版へコピーしない。既存のpublicメソッド名を維持し、保守・保護・分析を個別に呼べる入口を追加する。単一通貨版のイベント入口は従来の周期・呼び出し順を保つ。

全通貨版では、子Controllerが`EventSetTimer()`を呼ばない外部スケジュール方式を追加する。現在の`startTimer()`、`onTick()`、`onTimer()`を単純に28個ループすると、子ごとのTimer変更と重い分析が混在するため、そのまま利用しない。

## 4. イベントと巡回

### 4.1 LIVE

親Controllerだけが通常1秒Timerを所有し、次の順で処理する。

1. 全通貨のLock・Lease・DB再保存・取引状態を、各処理の既存間隔に従って確認する。
2. 全通貨の最新気配を確認し、保有・発注中通貨のpending SL、SL復元、候補跨ぎ決済を優先する。
3. 通貨ごとのH1バーを確認し、必要なトレイル分析とEntry分析を待ち行列へ登録する。
4. トレイル分析を優先しつつ、Entry分析も順番に進める。未準備の1通貨が全体を止めない。

重い分析は、初版では1回のTimerイベントにつき最大1通貨・1分析タスクを基本とする。分析タスクの間に全通貨の保護処理へ戻る。28通貨の分析を1イベント内で最後まで連続実行しない。解析時間・待ち時間を計測し、受入結果で処理枠を調整する。

各通貨の初回判定は最初の通常巡回から順次開始する。その後のLIVE再試行は従来どおり通貨ごとに30秒以上空ける。キュー待ちによる遅れは記録する。毎時の巡回開始位置を交代させ、特定通貨が常に最後にならないようにする。実行順は記録し、テスターでも再現できる固定規則にする。

判定済みH1バーは再判定しない。分析失敗は回数を消費せず再試行する。Judge成立後に発注安全条件でSKIPとなっても回数を消費する現行仕様は維持する。H1バーが切り替わった待ちタスクから、過去バーの遡及発注はしない。

`OnTick()`はチャート通貨について従来の保護処理を早める補助入口とする。他通貨の管理をチャート通貨のTick到着へ依存させない。TickとTimerで同じ保護要求を重複送信しないよう、既存のpending状態・要求ID・再試行時刻を共用する。

### 4.2 気配とバー

各通貨自身の`SymbolInfoTick(symbol)`と`iTime(symbol, PERIOD_H1, 0)`を使う。チャートのBid/Ask、Digits、バー時刻を別通貨へ流用しない。気配の時刻と取得時刻を保持し、無効な気配や対象バーより前の気配では新規判定を待機する。分析後・発注直前にも気配、バー、Spread、SL幅、取引環境を再確認する。

他通貨の保護判断は巡回時に取得した気配で行う。巡回間に一瞬だけ跨いで戻った価格を完全には捕捉できないため、単一通貨のTick起点管理と同一結果は保証しない。brokerへ設定済みのSLは別途有効である。全Tickの跨ぎ検出が必要なら、Tick履歴の増分読取りを別仕様として設計する。

1秒Timerは実行間隔の目標であり、処理遅延の上限保証ではない。1分析自体が長時間かかる場合は途中で割り込めないため、28通貨受入時に保護処理の遅延を測定する。

### 4.3 取引通知

`OnTradeTransaction()`はsymbol、注文・約定ticket、position identifier、request IDから対象Controllerへ振り分ける。通知種別によってsymbolが空の場合や、手動SL変更ではmagicが異なる場合もあるため、symbolとmagicだけで破棄しない。

判別不能な通知は短い再照合予約だけを全対象へ通知する。イベント内で28通貨の重い履歴照合・分析を連続実行しない。遅延した約定通知、SLによる決済、手動変更も対象通貨の既存復旧処理へ渡す。

## 5. 通貨ごとの状態と障害

SignalCount、判定済みバー、トレイル評価バー、最新気配、分析ハンドル、注文・ポジション・pending SL、DB保存待ち、Lock、Leaseを通貨ごとに保持する。

| 状況 | 動作案 |
|---|---|
| 履歴・指標の準備中 | 該当通貨を待機。他通貨は継続 |
| 分析失敗・気配なし | 該当通貨の新規判定を待機。準備済み状態と混同しない |
| 発注拒否・注文結果不明 | 該当通貨の既存照合・再送禁止規則を適用 |
| DB保存不可 | 対象の新規発注を停止。共通DB障害なら全通貨へ波及する |
| Lease喪失・期限到達 | 該当通貨のEAからの取引操作を停止。broker SLは維持 |
| 無効な設定・対象銘柄不存在 | 起動時に全体を拒否し、取得済み資源を解放 |
| 起動時のLock競合 | 全体を拒否。取得済みLock・Runを後始末し、他EAのポジションには触れない |

初期化では、全対象の設定と所有権を確認してから売買可能状態へ移行する。履歴待ちは初期化失敗とせず、既存ポジションの照合・保護を先に準備する。`OnInit()`から新規発注しない。

保護処理の継続可否は現行のLock・Lease・保存済み状態の規則に従う。DB障害時に新しい候補を推測して発注したり、期限を越えて管理権限を延長したりしない。

## 6. DB・識別子・再起動

LIVEは`mstng-h1-ea.sqlite`、TESTERは`mstng-h1-ea-tester.sqlite`を継続使用する。1起動を1つの実行グループとし、その配下に通貨別Runを28件登録する。Decision・Trade・Eventは既存の通貨別Runに保存する。

| 識別子 | 役割 |
|---|---|
| sessionUid（新規） | 28通貨をまとめた1回のEA起動 |
| runUid | sessionUid・symbol・H1・magicを含む材料から生成する通貨別UID |
| contextKey | 現行の通貨別復元キーを維持。LIVEではsessionUidを含めない |
| Magic Number | 現行EAコード12と通貨・H1・戦略の生成規則を維持 |
| lockScope | 現行のサーバー・口座・通貨・H1・magic・実行モードを維持 |

現行runUidの生成材料には通貨がなく、同一チャートで同一ミリ秒に子を作ると衝突し得るため、複数通貨版のUID生成には通貨を必須とする。TesterのcontextKeyは従来どおり通貨別runUidを含め、反復テストを分離する。

第3段階で`h1_ea_runs`へnullableな`session_uid`と検索索引を追加した。既存RunはNULLのまま保持する。親Run用の別テーブルは初版では作らない。設定記録に運用方式、固定通貨リストの版、巡回規則を残す。毎起動変わるsessionUidは設定hashへ混ぜない。

DBの初期スキーマ確認・移行は親が最初に完了させる。通貨別Persistence Serviceは既存構成を再利用し、同一EA内では順次呼び出す。他インスタンスとのDB競合では既存のbusy・再試行規則を適用する。28通貨全体を1つの長いtransactionで囲まない。

旧単一通貨版からの移行でもLIVEのcontextKeyとMagicを変えず、消費済みシグナル・既存ポジション・pending SLを通貨別に復元する。旧EAが同じ通貨を管理中ならLock競合で二重管理を拒否する。既存DBの判定結果は再計算・上書きしない。

終了時は新規処理の受付を止め、保存・照合・Run終了・Lock解放・ハンドル解放を通貨ごとに行う。EA終了を理由に保有ポジションを一括決済しない。

## 7. テスターとウォームアップ

28通貨版は複数通貨テストを対象とする。基準モデルは「リアルティックに基づいた全ティック」とし、「始値のみ」は本設計の受入対象外とする。

Testerも親の通常1秒Timerで全通貨を巡回する。チャート通貨のTickからの補助呼出しを認めるが、シミュレーション時刻・通貨別バー・最新気配・処理済み状態で重複を排除する。現在のシミュレーション時刻を越えた気配・履歴を判定へ使用しない。

単一通貨版は従来のTick起点Entryを維持する。全通貨版はTimer巡回による評価時刻の違いがあるため、全約定時刻・価格の完全一致を合格条件にしない。同じデータ・同じ評価時刻での戦略判定と回数管理を比較する。

売買開始前は28通貨の履歴準備を進め、波動の本分析・Judge回数消費・Entry Decision作成を省く。v1.09では、全通貨のDB復元・照合と口座全体の空状態を確認した後、Timerを停止する。初回と、その後テスト内1時間経過後のTickで28通貨をまとめて確認する。保有・発注中・未保存・DB異常や売買開始到達時は通常1秒Timerへ戻す。待機中のDB予約と操作権限の扱いは19節を参照。

各通貨のMN1〜H1の準備状況を独立管理する。準備済み通貨の判定を未準備通貨の完了待ちにしない。実行速度に左右される壁時計時間ではなく、テスト内時刻と固定巡回規則で分析順・再試行を決める。

### 7.1 観測版と共通の履歴準備

`H1EaStrategy`は[共通の履歴準備クラス](../../Include/Mstng/Util/ElliotHistoryPreparation.mqh)を使用する。H1観測・M5観測と履歴取得、同期・本数の確認、再確認間隔を共用し、波動分析、売買開始判定、DB・Lease・ポジション管理はEA側で行う。

Testerでは、1通貨の対象5足すべてで同期済みかつ次の必要本数を満たすことを「履歴準備完了」の条件とする。

| 時間足 | H1 EA・H1観測 | M5観測 |
|---|---:|---:|
| MN1 | 61本 | 61本 |
| W1・D1・H4・H1 | 各206本 | 各206本 |
| M15・M5 | 対象外 | 各206本 |

EAのLIVEは従来どおり系列同期を準備条件とし、今回の本数条件統一はTesterに限定する。LIVEの分析・売買条件へ新しい最低本数ゲートを追加しない。

| 期間 | 共通の履歴処理 |
|---|---|
| 初期化 | 基準足から上位へ、H1、H4、D1、W1、MN1の順に各500本を要求する |
| Tester・指定売買開始前 | 初回に同期・本数を確認し、以後はテスト内時刻で最短3,600秒ごとに再確認。不足系列の取得もこの間隔に抑える |
| 指定売買開始到達・時刻逆行 | 待機中の確認結果キャッシュを解除し、次の履歴確認で再評価する |
| 売買開始後・売買開始0・LIVE | 履歴確認の呼び出しごとに同期・必要な本数条件を再評価。不足系列への`CopyRates`再要求は最短60秒間隔 |

500本は取得要求であり、履歴準備完了の必要本数ではない。初期要求を基準足から始めることで、他通貨を最初に参照した足より下位を取得できない「始値のみ」の制約にも配慮するが、基準バックテストのモデルと受入範囲は変更しない。

開始到達のキャッシュ解除はH1途中に指定した日時でも行い、同じH1で履歴が準備済みだったことを理由に開始前の待機結果を使い続けない。EAの判定済みH1・売買開始条件は維持する。履歴準備だけが28/28でも分析成功・エントリー成立ではなく、逆に一部通貨の履歴不足で準備済み通貨を止める全体売買ゲートも追加しない。

30秒Timerで1通貨ずつ処理する親の巡回と、28通貨のDB heartbeat・保護処理は従来の周期で継続する。3,600秒の間引きは履歴の再確認・不足取得だけに適用し、DB管理を1時間に1回にする仕様ではない。分析Hash・DB形式は変更しない。

本共通化は重複確認と取得要求を減らすもので、必要本数の緩和やテスターの長期履歴の拡張ではない。実MT5での短縮率と長期履歴取得への効果は未確認である。

## 8. 状態表示とログ

28通貨の監視ができるよう、全体の稼働数・準備中数・新規停止数と、通貨別の準備状態、最終判定H1バー、保有状態、停止理由を表示する簡易一覧を提案する。表示は専用クラスへ分離し、Elliottのチャート描画は初版対象外とする。

既存LoggerのINFO・DEBUG・ERROR形式を維持する。起動時にsessionUidと各runUidの対応、設定、巡回規則を記録する。状態変化と異常を記録し、1秒ごとに28行を常時出力しない。分析所要時間・保護巡回の遅延は受入検証で計測する。

## 9. 実装単位と受入

1. 通貨ControllerのTimer依存を分離し、単一通貨版の既存動作を確認する。
2. 親Controller・28通貨登録・巡回・UID・Runグループ記録を追加する。
3. Timerからの全通貨保護と取引通知の振り分けを実装する。
4. 28通貨の判定・保存・テスター・ウォームアップを接続する。
5. 状態表示と仕様書を更新し、以下を受入確認する。

| 確認対象 | 合格条件 |
|---|---|
| 単一通貨版の回帰 | 既存のJudge・回数消費・初期SL・トレイル・復元テストが通る |
| 28通貨登録 | M5観測と対象・順序が一致し、重複UID・通貨状態の混入がない |
| 他通貨の更新 | チャート通貨にTickがなくても、Timerで他通貨の保護・判定が進む |
| 一時的な履歴不足 | 1通貨の不足で他通貨の判定が止まらない |
| 重複防止 | 同一H1バー・同一起点・方向の回数消費と発注が重複しない |
| 再起動・旧版引継ぎ | 消費済みSKIP、OPEN/PENDING、SL候補、遅延約定が正しく復元される |
| 同時起動 | 単一版・全通貨版の同じ通貨の二重管理を拒否する |
| DB・Lease障害 | 既存の発注禁止・保護継続期限を通貨ごとに守る |
| Tester | 反復実行で巡回規則・判定順が再現し、未来データを使わない |
| 負荷 | 28通貨の準備・毎時分析・複数保有時の遅延とメモリ使用量を測定する |

数値としての性能合格基準は、現行1通貨の計測と28通貨の試作結果から詳細設計時に定める。Timerの指定値だけを根拠に「全通貨を毎秒必ず処理」とはしない。

## 13. 第3段階の実装（2026-09-23）

以下は第3段階時点の記録です。最新の保護接続仕様は14章を参照してください。

`MstngH1EaAll` v1.01で、同じ起動の28通貨を共通`sessionUid`へまとめ、通貨別Run・Lock・LeaseとDB復元を接続しました。共通DBの物理schemaはv3です。単一通貨版もv3対応を識別するためv1.10へ更新し、戦略と既存設定のcanonical textは維持しています。

### 13.1 起動と終了

1. 全銘柄を確認し、共通`sessionUid`を作成します。
2. 各通貨の設定を検証し、単一通貨版と同じscopeのLockを全28通貨分取得します。どこかで競合したら全体を拒否します。

4. 子がDDL禁止でDBへ接続し、通貨別Runを順次登録・復元します。先に登録したRunのLeaseも起動中に保守します。
5. 全通貨のDB準備成功後、親の1秒Timerを開始します。

途中で設定・Lock・schema・Run登録・DB読取・Timer開始に失敗した場合は全体を起動失敗とし、登録済みの自分のRunを`FAILED`で終了して全Lock・接続・資源を解放します。DB障害でRun終了を書けなかった場合はログを残し、Lease期限で再起動時に回収されます。正常終了は`STOPPED`です。他のRunを終了対象にしません。

### 13.2 復元する情報

| 情報 | 第3段階の処理 |
|---|---|
| SignalCount | LIVEでは従来と同じcontextKeyで復元。消費済みSKIPも引き継ぐ |
| 判定済みH1バー | 通貨自身の現在バーが取得できてからDBを照会し、保存済みなら確定状態へ復元 |
| 未完了取引 | `OPEN_PENDING`等のactive TradeをExecutorへ読み込む |
| pending SL | 保存済みTradeに含まれる候補・起点・要求ID等をそのまま読み込む |
| 同一バー反転禁止 | 保存済みの禁止バーを読み込む |
| 監査欠落 | `AUDIT_STATE_LOST`として状態・ログへ反映 |

H1未取得はDB起動失敗にせず、`WAIT_H1`として後の巡回で判定済みバーを復元します。DB復元状態は`H1EaRestorationState`のコピーで取得できます。`DB_RESTORED`は保存情報を読み込めた状態です。brokerの現在の注文・ポジションとの照合は第4段階へ残しており、売買可能を意味しません。画面パネルはまだ追加していません。

複数通貨のDB準備モードでは、子の通常イベント入口・Entry・保護SL・トレイル・取引通知入口をガードし、Executorへ有効な取引権限を渡しません。終了時もbroker照合を呼びません。第3段階では新しいDecisionや取引Eventを作成せず、SignalCountを追加消費しません。

共通inputとしてロット0.01、最大初期SL幅100.0 pips、Tester売買開始日時2026.01.01を追加しました。設定を検証して各Runへ記録する段階で、まだ売買には使用しません。設定記録には`OPERATING_MODE=MULTI_SYMBOL_DB_PREPARATION`、`SYMBOL_LIST=M5_FIXED_28_V1`、`SCHEDULE=TIMER_1S_ROUND_ROBIN_V1`、`TRADING_ENABLED=0`を追記します。sessionUidは設定hashへ含めません。

## 14. 第4段階の実装（2026-09-23）

`MstngH1EaAll` v1.02で、全28通貨のポジション・注文照合、既存リスクの保護SL処理、H1 ZigZagトレイル、取引通知の振分けを接続しました。**新規Entryはまだ開始しません。** 単一通貨版は共通実装の更新を識別するためv1.11とし、既存のイベント周期・戦略を維持します。

### 14.1 起動と保護権限

全通貨のDB復元・Lock・Lease確認と親Timerの設定成功後に、子の`protectionEnabled`を有効にします。OnInitではbroker照合・SL変更・決済を行いません。設定失敗時は第3段階と同じく全体を拒否し、自分が取得した資源とRunだけを後始末します。

子の通常`onTick()`・`onTimer()`・`startTimer()`とEntry入口は外部巡回モードのガードで無効のままです。保護入口だけを明示的に許可します。送信直前のLock・Lease・保存済み状態・取引環境・再送間隔は既存Executorの規則を使用します。DB切断時も既知Leaseを越えて権限を延長せず、Lease喪失後の新しい操作を許可しません。

### 14.2 Timerの順序

| 順序 | 処理 |
|---|---|
| 1 | 全通貨のDB保守。Lease更新と保存待ちEventの再保存を確認 |
| 2 | 全通貨の現在H1を各通貨自身で取得し、broker照合と保留SL処理を実行 |
| 3 | 未処理のトレイルがある通貨を優先し、最大1通貨の履歴準備・分析を実行 |
| 4 | トレイル待ちがなければ、通常の履歴準備を1通貨進める |

トレイル対象と通常履歴準備には独立した巡回位置を持たせます。保有通貨が複数でも1回に28通貨の波動分析を連続実行せず、次の分析前に全通貨の保護へ戻ります。チャート通貨のTickではその通貨のDB保守・照合・保護だけを補助し、分析やEntryは呼びません。対象外のチャート通貨ならTick補助は省略します。

各通貨の起動時H1を基準として、以降の新規H1でトレイルを評価します。起動時にH1を取得できなかった場合は取得後に確認します。既に保存済みのトレイル評価バーはExecutorでも除外します。履歴準備待ちは同じバーで30秒以上空けて再巡回し、他通貨の処理を継続します。準備後の分析失敗は既存のトレイル見送り記録へ渡します。予約バーや分析結果のバーが変わった場合は、古いバーに新しい波動を記録しません。

### 14.3 接続した保護動作

単一通貨版の`reconcile()`・`processPending()`・`evaluateTrail()`を再利用します。保存済み取引と実際の注文・Position Identifierを照合し、初期SL・適用済みトレイルSLの復元、改善するZigZag候補の適用、候補価格を跨いだ場合の決済、部分約定の残注文取消・既存決済の再確認を行います。新しいEntry注文は作成しません。

価格は対象通貨自身のBid/Askを読みます。複数通貨版では気配時刻が正であること、現在H1が判明していればその開始より前でないこと、`TimeCurrent()`の当該秒末尾より未来でないことも確認します。秒数による新しいSpread・気配有効期間の入力は追加していません。TickとTimerは同じExecutor・pending要求ID・1秒以上の送信間隔を共有します。

1秒Timerは処理遅延の上限保証ではありません。分析中に割り込めない点や、他通貨で巡回の間に一瞬だけ価格を跨いだ場合を捕捉しきれない点は4章の制約を維持します。

### 14.4 取引通知

`OnTradeTransaction()`では対象の特定と軽量受付だけを行います。通知は到着順が保証されず、REQUEST型ではrequest/resultを参照する必要があるため、型を区別して振り分けます。[MQL5取引通知仕様](https://www.mql5.com/en/docs/constants/structures/mqltradetransaction)

1. 明示されたsymbolを確認します。REQUESTならrequest.symbol、それ以外はtransaction.symbolです。
2. symbol省略時は各Executorが記憶するPosition/注文/約定ticketと保留SLのrequest IDを照合します。
3. それでも不明なら現在Position・現在/履歴注文・約定履歴のticketからsymbolを取得します。
4. 判別不能・複数候補なら、全通貨へ完全な約定照合を予約します。通知内では全件照合しません。明示的な対象外銘柄は処理しません。

手動SL変更を落とさないよう、親はmagicだけで通知を除外しません。実際の取引帰属は既存Executorで確認します。対象が確定した銘柄省略DEAL通知は、コピーにsymbolを補完して約定監査キューへ渡します。決済済みTradeへの遅延通知も受付対象です。

`H1EaTradeExecutor.observeTradeTransaction()`を追加し、要求結果と約定ticketを先に保持します。重い照合・DB保存は後続のTimer/Tickで行います。単一通貨版の`onTradeTransaction()`は従来どおり軽量受付の直後に照合します。

### 14.5 保存・終了・設定

物理schema v3、LIVE contextKey・Magic・sessionUid・RunUIDの規則は変更しません。新しいRunのconfig_textには`OPERATING_MODE=MULTI_SYMBOL_PROTECTION_ONLY|SYMBOL_LIST=M5_FIXED_28_V1|SCHEDULE=TIMER_1S_PROTECTION_FIRST_V1|ENTRY_ENABLED=0|PROTECTION_ENABLED=1`を追記します。過去Runの設定は変更しません。

保護接続後はEvent保存待ちの再試行と、終了時の注文を送らない最終照合・Event保存・監査未完了検出を接続します。終了を理由にポジションを閉じません。DB復元状態のコピーには`protectionEnabled`と最後に確認したTradeを含めますが、フラグがtrueでも常時送信可能を意味しません。

既存のロット・最大初期SL幅・Tester売買開始日時は記録を維持します。第4段階は新規Entry未接続であり、この日時より前でも既存ポジションの保護は停止しません。全体ポジション上限、Entryスケジュール、複数通貨Testerの高速ウォームアップは後続段階です。

## 15. 第5段階の実装（2026-09-23）

`MstngH1EaAll v1.03`で、固定28通貨の新規Entryを接続しました。共有コードを使用する単一通貨版はv1.12です。H1戦略V2、Spread 5.0 pips以下、ZigZag初期SL・トレイルの判定規則は維持します。

### 15.1 判定・発注の流れ

1. 起動時に全通貨の設定・Lock・Run・DB復元を確認し、親の1秒Timerが開始できてから`enableProtection()`と`enableEntry()`を接続します。OnInit中には発注しません。
2. 各Timerで全通貨のDB保守とポジション保護を先に実行します。
3. 対象通貨の履歴準備と現在H1の判定済み状態をDBから復元します。復元した判定済みバーは再分析・再発注しません。
4. `processScheduledEntry()`が、自通貨の現在H1・履歴・気配・判定復元完了を確認します。
5. 通常版と同じ`evaluateEntry()`で分析・Judge・SignalCount更新・発注前安全判定を実行します。分析後にも現在バーと気配を確認し、変化していればJudge回数を消費せず戻ります。
6. Decision・Trade・ENTRY_REQUESTをDBへ保存できた場合だけ、既存ExecutorでOrderCheck・送信直前確認・OrderSendへ進みます。保存失敗では注文を送りません。

新規のpublic入口は`enableEntry()`、`getPendingEntryBar()`、`processScheduledEntry()`です。子の通常`onTick()`・`onTimer()`・`processEntry()`は外部巡回モードでは引き続き呼びません。親の専用入口から共通の内部判定を使用します。復元状態のコピーには接続状況を表す`entryEnabled`も追加します。

### 15.2 巡回順序と再試行

| 項目 | 実装 |
|---|---|
| 重い処理 | 1イベントで最大1通貨の履歴準備と、トレイルまたはEntryの1分析 |
| トレイル優先 | 重いトレイル処理を最大2回続けたら、次はEntryまたは履歴準備へ枠を渡す |
| 毎時の開始位置 | `floor(TimeCurrent() / 3600) % 28`。共通通貨リストの0始まりの位置から順に進む |
| 未取得通貨 | リソース未作成・H1未取得の通貨も巡回候補へ含め、他通貨のEntry再試行による放置を防ぐ |
| LIVEの再試行 | 通貨ごとに前回のEntry巡回開始から30秒以上。履歴・気配・DB復元待ちも対象 |
| TESTERの再試行 | 通貨ごとにテスト内時刻で1秒以上。通常版のTick判定は維持し、AllはTimer判定 |
| 判定済みH1 | 同じバーを再判定しない |
| バー切替 | 待機中の古いバーは実行しない。新しい現在バーの復元・分析へ進む |

トレイルを含む実行時間やTimerの遅延により、実際の巡回は上記最短間隔より遅くなります。`OnTick()`はチャート通貨の保護補助に限定します。毎Timerの全通貨保護は、重いトレイル分析の回数制限とは独立しています。

分析を開始した際は通貨別運用ログへ`SCHEDULE_ENTRY`を記録し、巡回候補として最初に観測してからの`queueWaitMs`とH1開始からの`barDelaySeconds`を残します。終了は`SCHEDULE_ENTRY_END / elapsedMs`です。これらの時間計測にはLIVEでは単調時計、Testerではテスト内時計を使用するため、TesterのelapsedMsは実CPU処理時間ではありません。履歴待ち段階だけで終わった巡回は分析開始ログを出しません。

### 15.3 重複防止・見送り・気配

SignalCountは通貨別contextから復元し、Judge成立後に発注安全条件で見送っても消費します。保有中・Spread超過などをJudge前の巡回除外条件にはしません。分析失敗・分析前後の気配不備・現在バーのDB照会未完了ではJudgeを実行しません。分析成功後のDB保存不可は新規発注を止め、既存の保存待ち処理へ渡します。

`hasCurrentEntryQuote()`は自通貨のH1が判定対象と一致すること、対象がサーバー現在時刻のH1期間内であること、有限で正しいBid/Ask、気配が対象バー以降かつ未来時刻でないことを確認します。他通貨のTickでサーバー時刻だけ進み、対象通貨のH1が古いままの場合も新規Entryは待機します。AllではOrderCheck後・OrderSend直前にもこの確認を行い、取得できなければ`OPEN_FAILED / ENTRY_QUOTE_UNAVAILABLE_BEFORE_SEND`として記録します。

分析を開始したが確定できなかった観測バーは、次の評価で既存の`ANALYSIS_UNAVAILABLE`保存対象となります。履歴・気配待ちで評価入口まで到達しなかった過去バーを全件埋め戻す仕様ではありません。

### 15.4 設定・DB・上限

物理DB schema v3、LIVE contextKey、Magic、sessionUidの規則は維持します。既存Runの設定・判定は変更しません。**全体上限は未追加で、通貨・Magicごとの1ポジション制限と発注中の重複禁止を継続します。** 基準テストでは最大28通貨の同時保有があり得ます。全体上限を決める入力や通貨集中フィルターは後続段階です。

Tester売買開始日時より前は新規Entryを巡回対象にせず、履歴準備と既存ポジション保護を継続します。全通貨版の高速ウォームアップ、MT5での複数通貨テスター受入は第6段階です。

### 16.1 高速ウォームアップへ入る条件

以下をすべて満たした場合だけ、親Timerを1秒から30秒へ切り替えます。

- Testerで、`InpTesterTradeStartTime`が0以外、現在時刻が開始日時の30秒より前。
- 全28通貨が起動・DB復元済みで、保護とEntryの専用入口が接続済み。
- 全28通貨のDB・SignalCount復元・Executor・Lock・Leaseが正常。期限切れ・監査欠落・未保存Decisionがない。
- 全Executorがbroker照合済みの空状態。保有・発注中・保留SL・未保存Event・約定監査待ち・過去取引の復旧対象がない。
- 対象外銘柄や別Magicを含め、口座全体のポジション数と注文数が0。

起動時はまず1秒Timerを設定します。初回の全通貨照合が完了するまでは高速化しません。履歴準備の完了は高速化条件に含めず、空状態を確認できれば28通貨の履歴を低頻度で準備できます。LIVE、開始日時0、開始日時到達後にはこの高速化を適用しません。

### 16.2 高速期間に行う処理

| 項目 | 動作 |
|---|---|
| 親Timer | 30秒周期。子ControllerはTimerを操作しない |
| 履歴 | 1回のTimerで1通貨を順番に準備。開始前の同期・本数再確認と不足取得は通貨ごとに最短3,600秒間隔。同じH1の準備済み通貨の省略は、開始到達時にも解除 |
| Tick | 安全条件・周期切り替え・必要時のDB保守を確認。履歴準備・波動分析は行わない |
| heartbeat | 各Runの前回heartbeatからテスト内30秒以上で更新。Lease有効期限60秒は維持 |
| 再確認 | 全通貨の保守後にも高速化条件を再確認。途中のDB異常を次回へ持ち越さない |
| 波動分析・Judge | 新規Entry用には実行しない。SignalCountを消費せず、Entry Decisionを作成しない |
| 判定済みH1照会 | 開始前は省略。開始後に選ばれた通貨で現在H1をDB照会してから判定する |
| broker照合・保護 | 照合済み空状態の間は反復を省略。安全条件が崩れたら通常処理へ戻す |

高速化できない開始前期間では、全通貨の通常保護を継続します。既存ポジションがある場合のトレイル分析も継続するため、「開始前は保護まで停止する」という仕様ではありません。

30秒に1通貨を処理するため、高速経路だけなら28通貨の1巡にはテスト内で約14分かかります。実時間の短縮率を保証する値ではありません。未準備の通貨があっても、開始後は準備済みの通貨から個別に判定へ進みます。

### 16.3 通常周期への復帰と失敗時

開始30秒前、保有・注文の検出、未保存状態、DB・Lock・Lease異常などで、親Timerを1秒へ戻します。チャート銘柄が28通貨に含まれなくてもTickから周期復帰を確認します。

通常周期の復帰時は、全通貨のDB保守待ちを解除します。高速経路から戻ったTickでは全通貨の保護を実行し、次のTimerだけに復帰を依存させません。Timer設定に失敗した場合も保護と保守は継続し、5秒以上空けて再設定します。Entryには`eventTimer.isNormalReady()`を渡すため、通常Timer設定の成功を確認できるまで新規判定・発注を保留します。

周期変更・復帰はTickまたはTimerイベントで観測します。指定秒数はイベント到着の上限保証ではありません。Lease期限へ到達した通貨の取引操作を許可するものでもありません。

取引はDB復元または最後のbroker照合値で、新しく価格・ポジションを照会した結果ではありません。「取引管理数」は保有だけでなく発注中・決済中・復旧待ちも含むため、現在の実保有ポジション数とは区別します。BUYは青系、SELLは赤系、準備中は黄色、新規停止は赤系です。

Memory MBは`MQL_MEMORY_USED`による当該EAの現在使用量です。端末全体の使用量や最大値ではありません。[MQL5メモリ計測仕様](https://www.mql5.com/en/book/common/environment/env_resources)

### 18.1 履歴準備の診断ログ（v1.08）

全通貨Testerの`processPreparation()`で`PREPARATION_HISTORY`を出力します。初回と、準備状態・理由・不足足・未同期足の変化を即時に通知します。取得本数や最古日時だけの変化、同じ状態の24時間経過では再出力しません。テスト内時刻が前回出力時刻より戻った場合は再出力します。履歴待ちの本文には不足足だけの同期状態・取得本数・必要本数・最古日時を記録し、READYは通貨・時刻・状態・理由の短い行にします。通常の履歴待ちはINFO、リソース初期化ERRORはERRORです。

継続する待機は親Controllerの`HISTORY_WAIT`へ集約します。最初の28通貨一括準備後（通常経路ではTimerが28回以上処理された後）、テスト内サーバー日付（`TimeCurrent() / 86400`）ごとに最大1行を出力します。`ready=件数/28`と、MN1・W1・D1・H4・H1の不足通貨数を表示し、未確認は`pending`、ERRORは`error`として区別します。不足数・pending・errorが0の項目は省略し、全通貨の履歴がREADYなら行自体を出しません。同日中の変化は子の個別ログで通知し、親の集約は翌日まで繰り返しません。日付が逆行した場合は、その日付で集約を再開します。

不足足と未同期足は共通履歴準備が実際に確認した時点のビット列を保持し、未確認と不足なしを区別します。子の診断と親の集約は取得済みの値だけを読み、追加の履歴取得・市場参照・DB処理・売買処理は行いません。Testerの親が重複して出していた個別の準備状態ログは抑制し、LIVEの状態変化ログは維持します。`METRICS`も全通貨準備中・管理取引なしの間は日次出力に抑えます（17.4参照）。

個別ログの出力先はテスターのログと、既存の`Common/Files/MstngH1Ea/Logs/<runUid>.log`（通貨別Run）です。親の集約は既存のTimerログ出力を使用します。画面パネル・基準CSVのON/OFFとは独立します。LIVEと単一通貨版には追加ログを出さず、分析待機・売買・Timer・履歴本数条件を変更しません。READYは価格履歴の準備条件を通過した意味で、波動分析・指標計算の成功やエントリー成立の保証ではありません。ログ削減によるテスター速度・出力負荷の改善は、実MT5での性能実測が未確認です。


## 19. Tick起点のウォームアップ（v1.09 / 2026-09-26）

| 段階 | 動作 |
|---|---|
| 起動 | 28通貨のOS Lock取得、DB復元、broker照合を行い通常1秒Timerで開始する |
| 待機へ移行 | 指定売買開始前、全通貨のDB・Lock・Lease・監査が正常で、保有・注文・保存待ち・復旧対象がないことを確認する |
| 初回 | 全28 Runの待機予約に成功してからTimerを停止し、28通貨をまとめて準備する |
| 継続 | 前回の一括準備から3,600秒以上経過したTickで28通貨を再確認する。間のTickでは状態確認だけを行いDBを書き込まない |
| Tick欠落 | Tickが来るまで処理しない。次のTickで現在時刻の準備を1回行い、欠落した時間の分を繰り返さない。時刻逆行時も現在値を再確認する |

### 19.1 DB予約と操作権限

通常のLeaseは60秒で、Tickが来ない休日などを1時間Timer停止で待つと失効する。このため、全通貨版TESTERに限定して`lease_expires_at=3000.12.31 23:59:59`を待機予約の識別値に使う。予約中はExecutorへ渡す操作権限を0にし、発注・SL変更を許可しない。初回予約前の通常Leaseが有効であること、Run ID・RunUID・sessionUID・context・TESTER・RUNNING・期待した期限を照合し、DBコミット成功後にメモリを更新する。期限切れの通常Leaseを復活させない。

毎時のheartbeatは予約を維持する。売買開始または待機解除時は、同じ所有権を照合して期限を現在時刻＋60秒へ戻す。失敗した通貨は予約フラグと操作停止を維持し、通常Timerで再試行する。28通貨の予約が途中で失敗した場合も、既に予約した通貨を解除して通常処理へ戻す。

異常終了した予約は、次回起動時に同じ28通貨のOS Lockをすべて取得した後、同口座・通貨・H1・Magicの旧TESTER予約だけを`INTERRUPTED`へ整理する。schema移行より先に整理し、別口座、LIVE、通常Lease、他の稼働主体の行を変更しない。通常終了は既存のRun終了処理を利用する。

## 20. EA評価損益の表示（v1.10 / 2026-09-26）

パネル上部に`EA評価損益 +12,340 JPY ｜ 保有 3`の形式で、対象ポジションの評価損益合計と実保有数を表示する。各通貨の一覧右端にも評価損益を追加し、金額を右揃えにする。小さいチャートでは評価損益と保有数を上下の要約行に分ける。全体合計と各通貨は同じ読取スナップショットを使用する。

| 項目 | 表示定義 |
|---|---|
| 対象 | このEAが管理する28通貨と通貨別Magicに一致する現在のポジション。手動取引や別Magicは含めない |
| 金額 | `POSITION_PROFIT + POSITION_SWAP`。手数料を含めず、確定済みの損益も含めない |
| 単位 | 口座通貨。上部と列見出しに明記し、口座通貨の小数桁へ丸めて3桁区切りで表示する |
| 符号・色 | 正は`+`と青系、負は`-`と赤系、丸めたゼロは符号なしの灰色。売買方向のBUY/SELL色とは別の意味 |
| 保有なし | 正常に読取できて対象ポジションがなければ金額0・保有0。発注中や復旧待ちを含む既存の「取引管理数」と区別する |
| 取得失敗 | `取得待ち`として扱い、部分合計や前回の値を今回の正常値として表示しない |
| 詳細 | 行・合計のツールチップへ口座通貨、保有数、確認サーバー時刻、SWAP込み・手数料除外を表示する |

金額読取と通常のパネル再描画はそれぞれ60秒間隔で制限する。LIVEは単調経過時間、Testerはテスト内時刻を使う。ページ操作やチャートサイズ変更では即時再描画する。前回読取から60秒未満なら金額キャッシュを使い、読取間隔や通常再描画の期限を後ろへ延ばさない。60秒以上経過していれば再取得の対象になる。イベントがない期間は更新せず、次のイベントで現在値を確認する。非表示パネル・非ビジュアルTesterでは表示用の読取と描画を省略する。

表示用の読取は売買判断や注文を行わず、損益表示をEntry・SL管理・SignalCount・DB保存の条件にしない。実MT5での表示、フォント・DPI差、更新負荷は別途確認する。
