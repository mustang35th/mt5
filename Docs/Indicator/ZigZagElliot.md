# ZigZagElliot

## DBアラート表示（v1.48）

M5・H1チャートに、同じ時間足のAlert DB保存済みアラート文字を重ねて表示できます。現在の波動分析・情報表・エントリー判定・メール送信は通常どおり動作します。DBラベルから分析を切り替える機能はなく、M5の過去の詳細比較には`ZigZagElliotAlertHistory`を使います。

入力グループ「07. DBアラート表示（M5／H1）」で設定します。

| 項目 | 既定値・意味 |
|---|---|
| DBアラートを表示 | `false`。`true`でM5・H1に表示。他の時間足では無効 |
| 表示Run対象 | `指定Run／最新Run`（既定）または`期間内の全Run` |
| 表示Run ID（全Runでは無効、0=最新Run） | `指定Run／最新Run`で使用。`0`は最初に見つかった最新一致Runを保持。正数は指定Run。`期間内の全Run`では入力値を使わない |
| 表示開始日（サーバー日付、0=制限なし） | `0`。開始日の午前0時を含む |
| 表示終了日（当日を含む、0=制限なし） | `0`。終了日の翌日午前0時を含まない |
| ENTRY成立のみ表示 | `false`。`true`は保存されたENTRY成立のみ |

参照先は既存の「Alert DBファイル名」「Commonフォルダを使用」です。「DB保存を有効化」がfalseでも、既存DBからの表示は使用できます。読み取り専用接続を使用し、DBやテーブルの作成・更新は行いません。

検索はチャートの通貨・時間足（M5またはH1）、実行モード（LIVE／TESTER）、現在の接続先サーバーに一致するRunに限定します。Run IDを明示した場合もモードとサーバー条件を適用し、不一致なら別Runへ切り替えません。サーバー名が未取得の場合は表示を待機します。

初回読込は通常の履歴準備と分析が成功した後です。その後は新しい表示足バー（M5では5分、H1では1時間）で一括更新し、同じバーでは読み直しません。スクロール・拡大縮小時はキャッシュから再配置します。`指定Run／最新Run`では、新しい保存Runが作られても表示中のRunを自動で切り替えません。`期間内の全Run`では各更新で全一致Runを取り込み、新しいRunも対象にします。解決Run IDの0は全Run検索を表し、一つのRunへ固定しません。DB読込失敗時は既知のキャッシュを維持し、次のバーで再試行します。表示状態・エラー・保存値不足件数はログに記録します。

発生足の時刻と判定Server時刻の両方が現在の`TimeCurrent()`以前の記録だけを読み込みます。Runの自動選択にもこの条件を先に適用し、描画時にも確認します。テスターでは未来の判定を先に表示しません。バー途中の判定は次回の表示足バー更新で表示されます。

M5は採用分析の保存文字、H1は元分析の保存文字（例：`H1[S-LATE] ▲5-5-3`）をMS Gothic・20pt、通常版と同じBUY／SELL・ENTRY色で表示します。通常版が同じ発生足に同じ文字・色を描画している場合はDBラベルを重ねません。保存値が異なる記録は区別して表示します。密集時の上下調整・引出線、採用分析の概要ツールチップは履歴表示と共通です。通常版と重なる場合は、通常ラベルへ同じDB保存値のツールチップを設定します。DB表示の解除・対象外への変更時は元のツールチップへ戻します（他処理が更新済みの内容は上書きしません）。M5の補正情報未記録の元文字には`[元分析]`を付けます。H1は補正対象外のため、元分析を通常の採用記録として表示し、この接尾辞や補正未記録の警告を付けません。表示位置は保存された対象足の開始時刻・始値です。必要な保存値が欠損したラベルは表示しません。

ツールチップはM5ならMN1・W1・D1・H4・H1・M15・M5の7足、H1ならMN1・W1・D1・H4・H1の5足を各1行とし、`分析方向/EMA200方向 主波.副次波 確定状態`を表示します。`B`はBUY、`S`はSELL、`確`は確定、`未`は未確定です。MN1のEMA200と未保存・判別不能な値は`—`です。補正時は全時間足を補正分析から読み、欠損を元分析で補完しません。補正未記録は元分析である旨を明記します。159文字を超える場合はServer判定日時、副次波の順に省き、対象の全時間足とJST判定日時を残します。極端に長い波動値はセル内に`…`を付けて省略します。詳細は[履歴ツールチップ仕様](ZigZagElliotAlertHistory.md#ツールチップ)を参照してください。

全Run検索は現在の検索条件内の各Alert IDを保持し、発生時刻・ID順で表示します。同じ基準ポイントでも別時刻の記録は残します。同じ場所のDBラベルは上下へずらします。通常ラベルと同じ時刻・文字・色の記録はその通常ラベルへ集約し、複数一致時のツールチップはID順で最後の記録になります。

例：9月7日以降のH1アラートを再起動前後も含めて見る場合、H1チャートで「DBアラートを表示」=`true`、「表示Run対象」=`期間内の全Run`、「表示開始日」=`2026.09.07`とします。表示終了日=`0`は上限なし、ENTRYのみ確認する場合は「ENTRY成立のみ表示」=`true`です。日付はサーバー日付で、JSTではありません。LIVE／TESTERやサーバーをまたいだ混在表示は行いません。

## テスターのウォームアップ軽量化（2026-09-19）

通常版v1.46では、テスターの履歴準備が完了するまで、GMMA・EMAの表示更新と通貨強弱の取得・表示更新を延期します。追加の入力設定は不要です。通常チャートの処理順序と、ウォームアップ完了後の分析・補正分析・Signal Count・CSV・Alert DB保存条件は変更しません。

ウォームアップの必要本数はMN1が61本、W1以下の各分析対象足が206本です。価格系列の同期と本数は毎回の`OnCalculate`で確認するため、同じM5バー内で非同期の履歴取得が完了した場合も、検知した呼び出しで通常処理を開始します。分析用ハンドルの初期化と最初の履歴要求は継続します。必要本数を満たしても指標の計算が未完了の場合は、従来どおり分析を再試行します。

テスターの初期ウォームアップ中は、未同期の時間足だけを再要求し、同じ表示足バー内の重複要求を抑えます。同期復帰を観測した足が再度未同期になった場合は、同じバーでも再要求します。準備完了後の同期回復は従来の再要求方式を維持します。進捗の詳細文字列は進捗率が変わった時だけ生成します。保存開始日時を待って分析を省略する処理は追加しません。

この変更は100%到達までの実行負荷を減らすもので、必要履歴本数や100%に到達するテスト内の日付を短縮するものではありません。

専用インジケーター`ZigZagElliotAlertHistory`で、指定したRun・期間内のM5アラートを一件ずつ選び、保存時点の最新Wave・波動番号・FE・SL候補をチャートへ表示できます。補正前後の切り替え・比較と波動のツールチップに対応し、表示時の再分析やDB更新は行いません。設定と再現範囲は[履歴チャート仕様](ZigZagElliotAlertHistory.md)を参照してください。

## テスターのAlert DB保存開始日時（2026-09-19）

通常版v1.45では、`datetime`入力`mtf3In3AlertTesterSaveStartTime`を追加します。既定値は`0`（保存開始日時の制限なし）です。`MQLInfoInteger(MQL_TESTER)`がtrueの場合だけ適用し、通常チャートでは実効値を`0`として扱います。指定日時はブローカーのServer時刻です。JSTへの変換は行いません。

DB保存の対象は、分析に使用した現在足の開始時刻`currentOhlcBarTime`が指定日時以上になったバーです。比較は`currentOhlcBarTime >= mtf3In3AlertTesterSaveStartTime`とし、指定時刻と同じ開始時刻のバーを含めます。指定日時が足の途中の場合は、その日時以降に開始するバーから対象になります。保存対象期間でも、従来の`isAlert`条件を満たさなければAlert行は生成しません。

履歴の準備ができた後は、保存開始日時より前も分析・補正分析・Signal Countの処理を継続します。保存開始時に分析状態やCountをリセットしません。日時条件を追加するのはAlert DBへの元分析・補正分析の一括保存だけです。Runは従来どおり初期化時に作成し、分析CSV・Alert検証CSVの出力条件は変更しません。

Runの既存`input_text`と`input_hash`には、指定した保存開始日時と実効開始日時を含めます。保存範囲の設定であり分析条件ではないため、`analysis_input_text`・`analysis_input_hash`へは追加しません。DBの列・スキーマバージョンも変更せず、既存Runを書き換えません。

DB保存が有効な場合、初期化時に保存開始方針をINFOログへ出力します。開始日時を指定したテスターでは、日時条件を初めて満たした分析バーと、初めてDB保存が成功したアラートを区別し、各Runでそれぞれ1回だけINFOログへ出力します。履歴準備完了のログは別に扱い、準備完了・保存対象期間への到達・最初のアラート保存を同じ意味として扱いません。

| 設定例 | 値 |
|---|---|
| 通貨・時間足 | GBPAUD・M5 |
| テスト開始 | `2021.01.01` |
| テスト終了 | `2026.09.19` |
| `mtf3In3AlertTesterSaveStartTime` | `2026.08.01 00:00:00`（Server時刻） |

この例では、履歴準備後から分析状態を引き継ぎ、Server時刻2026年8月1日以降に開始したM5バーのアラートだけをDBへ保存します。指定期間の履歴取得・分析成功や、保存開始日時ちょうどのアラート発生を保証する例ではありません。

## M5の補正分析によるエントリー判定（2026-09-19）

通常版v1.44・MstngEa v1.15では、元のM5 `isJudge()`通過を補正の前提にせず、元H4・H1の方向から補正要否を決めてから最終条件を判定します。両足がM5と同方向なら元の分析を採用し、片方だけ逆方向なら、その足だけをM5方向に変更した別の`correctedElliotAll`を生成します。両足逆方向は補正せず拒否します。EMA200・GMMA・Spread等の先行チェックは追加しません。

補正用はMN1からM5まで独立した分析を構築します。H1補正ではH1→M15→M5、H4補正ではH4→H1→M15→M5へ親波動の変化が伝わります。元のOHLC・Oscillator値をコピーし、分析方向を強制変更するのは指定したH4またはH1だけです。波動内部では時系列を再取得するため、全7足の直近2本のOHLC・バー時刻が再分析前後とも元の値と一致しない場合は補正失敗として拒否します。過去の全履歴を固定した再計算ではなく、値動きやデータ更新中には補正が採用されない場合があります。

`AbstractExpertAdvisor.analyze()`は`selectJudgmentElliotAll()`で採用する分析を1回だけ選択し、`setElliotAll()`で現在足・上位足・最新2点・方向の参照をまとめて設定します。`isJudge()`と`setEntry()`の分析方向・EMA200・GMMA・Spread・通貨強弱・波動・FEは同じ採用分析を参照します。M5のWave方向、最新点の通常点条件、主波1・3・A・C、3波・C波のFE上限161.8%は従来と同じ条件です。元のM5が波動条件外でも、補正後が条件を満たせば判定対象です。補正失敗時は元の波動で判定を続けません。H4・H1の許可波動番号は未決定のため、新たな上位足波動制限は追加していません。

補正後の指標値は元の観測値をコピーしたものです。原本は非所有の`sourceElliotAll`へ保持し、Signal Countの元M5ポイント時刻・方向、任意のH1表示波重複キー、DBの既存分析スナップショット・分析CSVは従来の元分析を使用します。新規エントリーの損切りは、判定に採用した分析の`lossCut.lc5`を使用します。Count加算後にFEを確認する既存順序も維持します。補正分析はM5戦略が所有し、次回分析開始時と破棄時に解放します。採用失敗時は前回の判定参照・表示リストを残しません。決済判定の`isExit()`では補正分析を選択せず、元の分析を使用します。

通常版M5のチャート上アラート文字は、判定に採用した分析からH1のWave方向とH1・M15・M5の波動ラベル（副次波を含む）を生成します。H1補正時は末尾に`[H1補正]`、H4補正時は`[H4補正]`を付け、補正不要の場合は付けません。文字サイズ・色・表示位置は従来どおりです。DB保存・EAシグナル表示用の`alertText`と元分析の`mailTitile`、通常チャートの波動線・ラベル・情報表は元分析を維持します。

通常版M5で補正を採用した場合、メール件名のアラート部分はチャート上のアラート文字と一致します。本文は日時・レート・通貨強弱を共通情報として1回だけ記載し、補正した時間足と変更前後の方向を示します。その後に「補正後全体：判定・損切りに採用」「補正前全体：比較用」の順で、損切りとMN1・W1・D1・H4・H1・M15・M5の全7足を同じ項目構成で記載します。補正不要時は従来の1セットです。送信対象フラグ・タイマー実行条件・検証メタデータは元分析の設定を維持し、実送信とメール検証ファイルには同じ件名・本文を渡します。

補正前後の分析は、以下のAlert DB保存仕様に従って同じアラートへ保存します。既存の時間足別保存値・分析CSVとその損切り欄は元分析のままで、補正採用時の新規注文SLとは異なる場合があります。最終判定結果のM5ラベルは採用した波動を表します。既存ポジションのSL更新・トレーリング・決済ロジックは変更しません。通常版M5 Alert Runの戦略バージョンは`MTF3IN3_M5_CORRECTED_WAVES_V12`です。H1・M15戦略、Listの抽出条件、M5観測Collectorは変更しません。

### Alert DBの補正前後保存

通常版とAlertAllのAlert Runは`schemaVersion = 7`を使用します。同じ`alert_id`に元分析と補正分析を関連付け、既存の時間足別分析・最新Waveポイントは元分析のまま保持します。補正採用時は、別の保存領域へMN1・W1・D1・H4・H1・M15・M5の全7足と各足の最新Waveポイントを追加します。全Waveの履歴を保存する仕様ではありません。

追加テーブルは`zigzag_elliot_alert_corrections`（補正メタデータ）、`zigzag_elliot_alert_corrected_timeframes`（補正後の時間足分析）、`zigzag_elliot_alert_corrected_points`（補正後の最新Waveポイント）です。

補正メタデータには、補正状態、補正した時間足と前後の方向、採用後のアラート文字、元と採用後のSL候補を記録します。元のアラート文字は既存親Alertの`alert_text`に保持します。`originalAnalysisText`・`correctedAnalysisText`には各分析の`getText()`全文を保存し、時間足別の既存列にない直前推進波の副次波情報なども本文に保持します。SL候補は分析時点の`lossCut.lc5`であり、brokerが受け付けた注文・ポジションの実SLを意味しません。

比較キーに使う元の`signalReferencePointTime`は変更せず、補正後の基準点時刻は`correctedReferencePointTime`へ別途保存します。保存対象は従来どおり`isAlert`が成立した分析です。`isJudge()`で拒否された分析は保存せず、最終EntryでFE等により拒否されても`isAlert`が成立していれば保存します。

| 補正状態 | 意味 |
|---|---|
| `NONE` | 新方式で補正なしを確認。元分析を採用し、補正側の時間足・ポイントは追加しない |
| `APPLIED` | 補正分析を判定に採用。補正メタデータと補正側7足・最新Waveポイントを保存 |
| `UNRECORDED` | 補正情報を保存していない旧行。補正なしとは判断せず、後から補正値を埋めない |

既存の親Alert列は互換性を維持します。`is_entry`・`entry_result`・`current_elliot_label`などの判定結果は採用分析に基づく一方、既存の`alert_text`・`stop_loss`・`risk_pips`および元の時間足・ポイントは元分析に基づきます。補正前後の比較には、追加したメタデータと補正側スナップショットを使用します。既存の分析CSV・Alert検証CSVの列や値の意味は変更しません。

親Alert、元の時間足・ポイント、補正メタデータ、補正側の時間足・ポイントは1トランザクションで保存し、途中失敗時は全体を取り消します。同一アラートを再保存した場合は、最初に保存した全体を保持し、補正情報だけを後付けしたり置き換えたりしません。AlertAllのH1も同じ保存経路を使い、補正状態は`NONE`です。

Viewerのアラート一覧では、M5詳細を全画面グリッドで開き、補正採用時は「補正後（採用）」を初期表示します。「補正前」「前後比較」へ切り替えられ、比較では時間足ごとに補正後・補正前の2行を並べます。変更セルを黄色で強調し、BUY青系・SELL赤系を維持します。「要点のみ／すべて表示」「差がある列のみ」で列を調整できます。ENTRY結果と採用SL候補は表示切り替えで再判定・変更せず、元SLは比較用として併記します。最新Waveポイント・分析本文も前後を確認できます。直前推進波の副次波は保存本文で確認し、独立した数値列を推測補完しません。

旧DB・旧行は「補正情報未記録」、保存情報の不足・不整合は「補正データ不完全」とし、元分析を補正後として代用しません。M5ではH1用の参考判定を生成せず、保存済みM5判定を表示します。詳細は[Viewer README](../../Services/ZigZagElliotAlertViewer/README.md)を参照してください。H1/M5観測DB・観測Collector・MstngEaの取引履歴保存経路には追加しません。

## M5分析方向のH4・H1をOR化（2026-09-13）

通常版v1.43・MstngEa v1.14では、M5エントリーの分析方向条件を「W1＝D1＝M15＝M5、かつH4またはH1がM5と同方向」に変更します。H4・H1は両方一致でも許可し、両方逆方向なら拒否します。両足の分析データは引き続き必要です。

`isTimeFrameAnalysisDirectionConditionMatched()`をM5専用に上書きし、既存の`ElliotAll.isBuySellH4OrH1AndM15()`を再利用します。W1・D1一致とMN1分析方向またはW1 EMA200の一致は、既存の共通上位足判定で確認します。H1・M15を現在足とする戦略のD1までの分析方向一致は維持します。

EMA200はD1・H4・H1・M15・M5すべてM5分析方向との一致が必要です。波動・FE・GMMA・通常点・Spread・Signal Count・任意フィルタ・メール送信条件は維持し、EMA200距離は制限なしです。通常版M5 Alert Runの戦略バージョンは`MTF3IN3_M5_H4_OR_H1_V11`です。

## M5主波を1・3・A・C波へ変更（2026-09-13）

通常版v1.42・MstngEa v1.13では、M5エントリーの波動番号条件をM5の最新主波ラベル`1`・`3`・`A`・`C`だけに変更します。M5判定でのH1・M15の波動番号制限は外します。副次波は判定に使用せず、表示が`C.iii`でも主波`C`として扱います。入口の波動条件と最終Entry判定は同じM5専用`isEntryWave()`を使用します。

3波とC波はFEが有効な正数で、小数1桁へ丸めた値が161.8%以下の場合だけ許可します。未取得・無効値・0以下は拒否し、161.8%ちょうどは許可します。1波・A波にはFE制限を追加しません。FE拒否コードは3波が`M5_ELLIOT3_FE_REJECTED`、C波が`M5_ELLIOTC_FE_REJECTED`です。

## H1のEMA200確認（通常版v1.34）

通常の`ZigZagElliot`では、`h1Ema200ConfirmationMode`をinputから外し、`const`定数の`H1_EMA200_CONFIRMATION_H1_AND_H4_AND_D1_REQUIRED`に固定します。「EMA200確認（追加条件）」はinput一覧に表示しません。

H1エントリーでは、H1・H4・D1のEMA200がすべて同方向であることを必須とします。通常版ではH1のみ／H1・H4のみへ切り替えることはできません。

基準はH1の分析方向（`isBuy`）です。BUYなら対象足のEMA200がすべてBUY、SELLならすべてSELLであることを要求します。対象足のNONE・BUY/SELL両方向成立・方向不一致・取得不能・時間足不整合はNGです。D1の分析方向とD1のEMA200方向は別条件です。

固定値はv1.33の初期値と同じです。共通クラスの従来2モードと値0・1は、他プログラム向けに維持します。H1のEMA200距離制限は引き続き無効です。W1・MN1の方向条件、波動条件、Spread、Signal Countおよび判定タイミングは変更しません。

### 既存チャートへの適用

v1.34へ更新し、通常の`ZigZagElliot`を再読み込みしてください。旧チャート／setファイルに保存された`h1Ema200ConfirmationMode`では固定値を変更できません。以前H1のみ／H1・H4のみを選択していた場合も、更新後はH1・H4・D1の3足必須になります。

`ZigZagElliotList` v1.31のH1アラートと`MstngEa` v1.08のH1・`MTF_3in3`も3足必須を初期値にします。保存済みinputを使う場合は各EMA200確認モードを明示的に変更してください。従来の2モードも選択できます。`MstngH1Ea` v1.07は、v1.06で導入した3足必須固定と戦略バージョン`H1_MTF3IN3_EMA3_SPREAD5_ZIGZAG10_V2`を維持します。EMA200以外の各プログラム固有の判定・評価周期は変更しません。

`ZigZagElliotList`のH1主一覧には、H1方向を基準とした3足一致の参考表示`EMA3 OK`・`EMA3 NG`・`EMA3 ?`を追加します。H1＋M5モードでは上段H1が対象です。一覧の表示対象、D1優先ソート、READY順位、M5独立判定は変更しません。この参考表示はアラートの確認モード選択とは独立します。

Runの設定記録には実際に使用するEMA200確認モードを保存します。通常版v1.34では固定値の`H1_AND_H4_AND_D1_REQUIRED`を記録します。既存Alert／H1 Observation DBのスキーマ変更や保存済み判定結果の更新は行いません。H1 Observationの検索でEMA200 D1を指定すると観測の絞り込みを確認できますが、Signal Countに関わる実際のエントリー時刻の変化はテスターで確認してください。

`MstngH1Ea`の専用DBだけは、v1.07のRun登録前の初期接続フェーズ（失敗時の再試行を含む）に物理v2へ移行し、Decision末尾へD1 EMA200方向の個別列を追加します。正しい保存済み診断からD1列だけを補完し、未記録・`~`はNULL、`NONE`は評価済み中立として残します。診断テキスト・hash・過去のJudge判定は変更しません。DB内に未失効`RUNNING` LeaseやDecisionの独自triggerがある場合、またはschema・診断が不正な場合は移行を拒否します。Run登録後の再接続ではDDLを実行しません。更新前に同じDBを使う旧版EA・テスターをすべて停止してください。TesterのLeaseはテスト内時刻のため、異なるテスト期間間のWriter停止をLease比較だけでは保証しません。今回の実装作業で運用／Tester DBを直接変更するものではありません。詳細は[MstngH1Eaデータベース設計書](../Database/MstngH1EaDatabase.md)を参照してください。

Viewerの`H1 ENTRY CHECK`は保存時のRun設定を使い、H4・D1を必須／対象外に分けます。設定が未記録・不正の場合やH1 Observationでは参考表示とし、現在の初期値から過去のモードを推測しません。保存済みENTRY結果と研究用FULL・Episodeの定義は変更しません。
