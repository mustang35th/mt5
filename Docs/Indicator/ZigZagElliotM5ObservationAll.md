## 2. 目的と対象範囲

全28通貨について、M5新規足ごとの市場状態を上位足込みで記録する収集専用インジケーターを作成する。H1との方向一致やエントリー条件で収集対象を絞らず、後から条件成立前後を比較できるデータを残す。

### 2.1 初期版で行うこと

- 各通貨のM5境界を検出し、MN1からM5までの7時間足を分析する。
- 対象M5内で最初にSnapshot生成まで成功した結果を固定する。
- 取得済みSnapshotをFIFOへ保持し、専用SQLite DBへ直列保存する。
- 分析結果に加え、取得時点・解析時間・解析試行回数を記録する。
- 状態パネルで準備、分析、保存、キュー、欠損および取得品質を確認できるようにする。

### 2.2 初期版では行わないこと

- 売買注文、決済、ポジション管理、エントリー可否判定、アラート送信。
- H1方向と一致するM5だけを選別する処理。
- M5バー途中の全tick・全条件変化の保存。
- 過去の観測欠損を現在の分析結果から埋めるバックフィル。
- 全ZigZagポイント配列、全Wave履歴の保存。
- Episode化、将来損益、MFE・MAEの計算。
- 既存ViewerのM5対応、および既存H1研究処理のM5対応。

これは「5分ごとの観測」であり、5分の途中に一時成立したシグナルや、別チャートのアラート発生を完全に再現する記録ではない。

## 3. 全体構成と共通化方針

```text
ZigZagElliotM5ObservationAll（新規）
  ├─ M5観測設定：28通貨・M5基準・7時間足
  ├─ 収集制御：LIVE OnTimer / TESTER OnCalculate
  │    ├─ シンボル解決・履歴準備・境界検出
  │    ├─ 共通ElliotAllによるMN1→M5分析
  │    ├─ 観測Snapshot＋取得品質の固定
  │    └─ FIFO・単一Writerによる保存
  └─ M5収集状態パネル

M5専用SQLite
  ├─ 実行情報（Run）
  └─ 観測本体（1通貨・1M5）
       ├─ 時間足別分析（7行）
       └─ 取得品質（1行）
```

入口のインジケーターはH1版とM5版で分離する。内部では時間足に依存する観測条件を分離し、収集・Snapshot生成・DB保存の既存部品を必要な範囲で共通化する。

| 部品 | 設計方針 |
|---|---|
| 共通Elliott計算 | 既存の`ElliotAll`と計算パラメーターを利用。M5専用の波動計算式は作らない |
| 観測Profile | `ZigZagElliotObservationProfile`でH1／M5の基準足・足順序・識別値を管理 |
| 収集制御 | 既存`H1ElliotObservationAllController`を固定Profile対応にし、M5用の薄い`M5ElliotObservationAllController`から利用。境界検出、再試行、FIFO、Run管理を共通利用 |
| Snapshot Builder | 指定Profileの足数・順序・アンカーを使用して既存項目を変換 |
| 保存検証 | H1は既存5足、M5は7足として厳密に検証。任意足数を無条件に受け入れない |
| 取得品質 | M5の追加Entity／DAOとして分離。H1には保存を要求しない |
| 状態表示 | 表示責務を収集・判定・ハンドル管理から分離する |

既存H1 Controllerと状態表示クラスのpublic名は互換性のため維持する。関係のないEA・Listのリファクタリングは行わない。

観測Profileは起動時に選択して固定し、収集制御・Builder・保存検証・Hash生成が同じ定義を参照する。H1とM5の同時稼働で設定が入れ替わらないよう、共有グローバル値によるモード切り替えは行わない。

### 4.1 保存時間足と順序

| `time_frame_order` | 時間足 | `is_anchor_time_frame` |
|---:|---|---:|
| 0 | MN1 | 0 |
| 1 | W1 | 0 |
| 2 | D1 | 0 |
| 3 | H4 | 0 |
| 4 | H1 | 0 |
| 5 | M15 | 0 |
| 6 | M5 | 1 |

保存時間足数は7に固定する。既存の通常版・ListのM5解析と同じ系列であり、M30とM1は含めない。時間足、足数、足順序、28通貨および計算パラメーターはinputにしない。

### 4.2 分析値と履歴準備

上位足も各M5観測時点で再分析する。同じH1・H4バー内でも、形成足OHLC、shift 0のStochastic・GMMA・ATRや波動は変化するため、上位足のバー開始時刻だけをキーにした分析結果キャッシュは初期版では行わない。計算用ハンドルは再利用する。

EMA200の終値位置・傾きなどは現行Profileの参照shiftを維持し、MN1のEMA200計算省略も維持する。保存後に上位足が確定しても、過去Snapshotを確定値に置き換えない。

| 系列 | 最低バー数 |
|---|---:|
| MN1 | 61 |
| W1・D1・H4・H1・M15・M5 | 各206 |

共通の`ElliotHistoryPreparation`で全7足の系列同期と上記最低本数を確認し、すべて満たした通貨を「履歴準備完了」とする。H1観測・H1 EAのTESTERと同じ確認方法を使い、M5版は対象足にM15・M5を追加する。Elliott分析成功、保存開始日時到達、全28通貨の保存ゲート、DB利用可能は別に判定する。

初期履歴取得は基準足から上位へ、M5、M15、H1、H4、D1、W1、MN1の順に各500本を要求する。500本は取得要求であり、履歴準備完了の必須本数ではない。最上位ZigZagの最大計算範囲300本も、全系列の最低本数ではない。M5版でもMN1履歴が必要であり、M5の履歴だけでは履歴準備完了にならない。初期要求を基準足から始めることで、他通貨を最初に参照した足より下位を取得できない「始値のみ」の制約にも配慮するが、この変更だけでモデル別の実動作を保証するものではない。

| 期間 | 共通の履歴処理 |
|---|---|
| TESTER・指定保存開始前 | 初回に同期・本数を確認し、以後はテスト内時刻で最短3,600秒ごとに再確認。不足系列の取得もこの間隔に抑える |
| 指定保存開始到達・時刻逆行 | 待機中の確認結果キャッシュを解除し、次の履歴確認で再評価する |
| 保存開始後・保存開始0・LIVE | 履歴確認の呼び出しごとに同期・本数を再評価。不足系列への`CopyRates`再要求は最短60秒間隔 |

開始到達のキャッシュ解除は基準M5の途中に指定した時刻でも行う。保存候補の規則は変えず、`18:03`指定なら最初の保存候補は`18:05`となる。11.1節の保存開始前の全通貨巡回・事前分析の1時間間引きは維持し、共通クラスによる履歴確認の抑制とは別に扱う。履歴の共通化では分析Hash・DB形式を変更しない。

テスターへ渡される開始前の履歴には所定の範囲があり、端末に長期履歴ファイルがあるだけでは、短いテスト期間の冒頭から必要な上位足本数が見えるとは限らない。公式仕様でも必要本数が足りない場合はテスト開始を前へずらし、処理開始日まで待つ方法を案内している。本インジケーターではテスト期間の開始と`observationTesterSaveStartTime`を分けて設定する。[MQL5：マルチカレンシーテストの履歴と同期](https://www.mql5.com/en/book/automation/tester/tester_multicurrency_sync)

履歴処理の共通化は重複確認と取得要求を減らすもので、必要本数の緩和やテスターの長期履歴の拡張ではない。実MT5での短縮率と長期履歴取得への効果は未確認である。

### 4.3 M5の履歴不足ログ

M5版では必要本数または同期条件を満たさない時間足について、`ANALYSIS_HISTORY_UNAVAILABLE`に通貨・時間足ごとの実本数（`bars`）／必須本数（`required`）、取得できる最古のバー時刻（`first`）、同期状態（`sync`）を出力する。正常な足を毎回並べず、不足している足を確認できるようにする。

不足の初回は即時に出力し、その後は状態が変化していても最短1時間、不変なら24時間の間隔を空ける。テスターでは模擬サーバー時刻で間隔を判定するため、PC上で1時間待つ意味ではない。系列の復旧は検出時に`HISTORY_READY`を1回出力するが、これは系列同期と必要本数がそろったことだけを示す。Elliott実解析の成功、全28通貨の開始ゲート開放、DB保存の完了とは区別する。H1版のログ動作は変更しない。

## 6. DBファイルと誤指定防止

既定の保存場所は次とする。

```text
Terminal\Common\Files\mstng-zigzag-elliot-m5-observation.sqlite
```

Common使用を無効にした場合は、その端末の`MQL5\Files`へ保存する。長期研究・テスターモデル違い・条件違いの比較は、期間や試行名を含む別DBファイルで管理し、既存データの削除で再実行先を作らない。

### 6.1 DB確認の順序

1. 既存ファイルの場合は、テーブル・Run・観測の識別情報を読み取りで検査する。
2. 空の新規DB、または対応するM5観測用DBだけを書き込み対象として許可する。
3. H1／AlertのRunや観測があるDB、M5以外との混在DB、不明な既存形式は拒否する。
4. 許可後に限り、書き込み設定、テーブル準備、対応済みmigration、Run保存を開始する。

拒否対象ではDDL、migration、Run INSERT、WAL切り替えなどの書き込みを行わない。観測0件でもH1／AlertのRunだけがあるDBは拒否する。ファイル名だけで用途を判定せず、既存データの足種・Run識別値も確認する。

DBロックや一時的な接続失敗は通常の再試行対象とし、別用途DBの指定は運用エラーとして区別する。異常なDBを自動修復・削除しない。

初版の判別は`ZigZagElliotObservationDatabaseGuard.inspectM5()`で行う。空DB、または現行4テーブル・14明示索引の完全な定義と一致するDBだけを許可する。定義は`sqlite_master`から順序固定で読み、文字列リテラルを保持して正規化したSHA-256で比較する。CHECK・外部キー・UNIQUE・余分なトリガーも識別対象とし、部分スキーマ・未対応形式への自動migrationは行わない。RunのM5識別値と親観測のM5基準・7足・実行元整合も検査する。

専用Contextは既存ファイルを読み取り専用で検査し、RW接続後も設定・DDLの前に再検査する。4テーブルの初期化自体も1トランザクションとし、失敗時に部分スキーマを残さない。共通JST処理にはM5向けの「現行列を検査して索引だけを準備する」経路を追加し、既存H1のmigration経路は維持する。

v1.03は初版4テーブルと、`previous_motive_sub_elliot_index`列追加後の4テーブルを用途検査で許可する。許可済みM5 DBだけにスキーマ準備トランザクション内で新列を末尾追加する。新規DBも初版DDLの作成後に同じ追加処理を適用し、既存行の値・hashを更新しない。再接続では列の存在確認のみ行う。追加後のDBは旧版Collectorの物理スキーマ検査では拒否されるため、収集にはv1.03以降を使用する。H1 DBの列追加・保存・hashには適用しない。

### 6.2 接続とRun

- H1版とは別DB・別Runを使用する。
- 1回の起動では28通貨を単一Runへ関連付け、単一DB接続で直列保存する。
- 許可されたM5 DBには既存同様の外部キー有効化、WAL、DB待機・再接続規則を適用する。
- DB再接続でRunを作り直さず、同じRun情報を再利用する。
- M5の収集前・保存前に実行元server／loginを確認する。Run固定後の口座変更は収集停止とし、別口座の観測を混在させない。
- `schema_version`はRunの保存形式メタデータであり、物理DB全体のバージョンと混同しない。M5初版は`1`。既存H1の`6`および過去Runの番号は変更しない。

## 7. テーブルと保存項目

| テーブル | 関係・責務 |
|---|---|
| `zigzag_elliot_alert_runs` | 起動ごとの設定、実行元、計算・プログラムのバージョン |
| `zigzag_elliot_observations` | 1通貨・1M5・1分析Profileの観測本体 |
| `zigzag_elliot_observation_timeframes` | 観測本体1行に対して7行 |
| `zigzag_elliot_observation_capture_metrics` | M5観測本体1行に対して品質情報1行。新規 |

`alert_runs`という既存名称は互換性のため維持する。アラート発生や送信を意味しない。

### 7.1 観測本体

既存の親テーブルの列定義を利用する。主要項目は以下とする。

- `run_id`、`source_mode`（LIVE／TESTER）、`source_server`、`symbol_name`。
- `anchor_time_frame`／表示文字列、`anchor_bar_time`／表示文字列。
- `anchor_jst_time`／表示文字列、`capture_phase`。
- `spread_pips`、`pip_size`。
- `analysis_version`、`analysis_input_hash`、`snapshot_hash`。
- `time_frame_count = 7`、`created_at`／表示文字列。

バー時刻は各通貨の`iTime(symbol, PERIOD_M5, 0)`を正本とし、JSTは既存の`TimeJapanUtil`による変換値を保存する。取得が遅れてもバー開始時刻を取得時刻へ置き換えない。

`created_at`は既存形式との互換項目であり、取得遅延の計測には使わない。正確な時計の区別は品質情報側に持たせる。

### 7.2 時間足別分析

既存の時間足別列を7足すべてへ適用する。

| 分類 | 保存内容 |
|---|---|
| 方向 | `isBuy`、表示ラベル、Oscillator方向 |
| Wave | Wave数、最新Wave、確定、推進／修正、上昇／下降 |
| Elliott | 最新番号・ラベル、副次波番号・ラベル、直前ラベル |
| 最新ZigZagPoint | 価格、時刻、バー位置、経過本数、pips差、山谷、補完、補正、元の番号・ラベル |
| F・FE | 最新点のF、深度ゾーン、FE、Expansion価格情報と利用可否 |
| OHLC | 各時間足の現在形成足と直前確定足のOpen／High／Low／Close |
| 指標 | Stochastic、GMMA、ATR14、EMA200の位置・傾き・距離・方向など |

v1.03では7足それぞれに`previous_motive_sub_elliot_index INTEGER NULL`を追加し、観測時点の`Wave.getPreviousMotiveSubElliotIndex()`を保存する。現在2・3波では1波、現在4・5波では3波の副次波を確認し、該当する波番号`1`または`3`、副次波なし・対象外なら`0`を保存する。過去行は`NULL`（未記録）のままとする。保存時とDB制約で値を`0・1・3`に制限し、NULLは過去行用に許可する。M5のINSERT・bind数は88、H1は従来の87を維持する。

各時間足の最新点1件を中心とする構造化スカラーであり、全ポイントの保存ではない。追加項目は同じWave内の直前推進波に副次波があるかを表し、前のWaveの最終ラベルとは別である。過去推進波の個々の副次波番号・ラベル・価格・F／FEの完全な復元には、別の保存設計が必要となる。

F・FEと再分析前番号も現行ソースから取得する。最上位足の元番号設定修正を含む現在の解析を利用する。既存H1 DBの過去値を書き直さない。

### 7.3 Spreadと気配時刻

M5版は解析開始時の同一`MqlTick`からBid・Ask・更新時刻を一組で採用する。そのBid・AskでSpreadを計算し、対応する`time_msc`を品質情報へ保持する。Snapshot生成時やDB保存時に価格を再取得して差し替えない。

従来の`TodayRate`更新経路はBidとAskを別取得し、採用気配時刻を保持しない。M5は追加した`ElliotAll.analyze(const MqlTick&)`から`TodayRate.update(MarketContext&, const MqlTick&)`へ同一気配を渡し、Builderへもその気配を渡す。通常版・H1・EAの既存更新経路は維持する。

Bid／Askが非有限、非正、またはAsk < Bidの場合はSnapshotを生成しない。`pip_size`は対象シンボルのPoint・Digitsから現行規則で取得し、有効な正数を必須とする。高Spreadを理由に観測を除外しない。

`SymbolInfoTick`自体が失敗した場合はSnapshotを生成せず再試行し、別取得のBid・Askへfallbackしない。取得に成功して価格が有効でも、時刻だけを取得できない場合はNULLとし、現在時刻で補完しない。古い気配はその時刻を保持して品質確認に利用する。新しいM5への移行を示す場合は境界を再確認し、古いM5へ結果を付け替えない。

## 8. 取得品質テーブル

`zigzag_elliot_observation_capture_metrics`をM5専用DBに追加する。H1の親・子テーブルへの列追加は不要とする。

| 列名 | SQLite型 | 制約・意味 |
|---|---|---|
| `observation_id` | INTEGER | PRIMARY KEY。観測本体への外部キー、削除時CASCADE |
| `quote_tick_time_msc` | INTEGER | 採用した気配の更新時刻、ミリ秒単位。未取得NULL、記録値は正数 |
| `capture_market_time` | INTEGER | Snapshot確定時の`TimeCurrent()`、秒単位。未取得NULL、記録値は正数 |
| `analysis_elapsed_ms` | INTEGER | 成功した解析1回の実経過ミリ秒。未計測NULL、0以上 |
| `capture_elapsed_ms` | INTEGER | 当該通貨・M5バーの初検出からSnapshot確定までの実経過ミリ秒。未計測NULL、0以上 |
| `analysis_attempt_count` | INTEGER | 当該M5の観測用実解析回数。未取得NULL、成功Snapshotの記録値は1以上 |

品質行の存在と、個別の計測値が利用可能であることは区別する。新規M5観測には品質行を必須とするが、未取得値を0で埋めない。MQLのEntityでは利用可否フラグ等でNULLと有効な0を区別し、DAOでSQLへ変換する。

### 8.1 時計の意味

`capture_market_time`は市場時刻であり、実際の処理完了を表すPC時計ではない。`OnTimer`の`TimeCurrent()`は対象銘柄に限らない最後の既知の気配時刻であり、TESTERでは模擬時刻になる。[MQL5 TimeCurrent](https://www.mql5.com/en/docs/dateandtime/timecurrent)

実経過時間は`GetTickCount64()`の差で計測する。TESTERで`TimeLocal()`も模擬サーバー時刻となるため、日時の差を実解析時間の代わりに使わない。[MQL5 GetTickCount64](https://www.mql5.com/en/docs/common/gettickcount64)、[MQL5 TimeLocal](https://www.mql5.com/en/docs/dateandtime/timelocal)

- `capture_market_time - anchor_bar_time`は「市場時刻上の取得遅れ」として参照時に算出する。通信遅延や実経過時間とは呼ばない。
- 負の差や時計不明を0へ丸めて正常扱いせず、確認対象とする。
- `capture_elapsed_ms`の起点はバー開始ではなく、当該通貨の当該バーを初めて検出した瞬間である。
- 対象7時間足の解析は順次取得であり、同一tickで原子的に取得したことは保証しない。
- 品質時刻を取得できなくても、別の時計や`created_at`へfallbackしない。

### 8.2 計測と固定の範囲

- `analysis_elapsed_ms`は、最終的に採用した`ElliotAll.analyze()`呼び出し前後のカウンター差とする。DB書き込み時間は含めない。
- `capture_elapsed_ms`には初検出後の順番待ち、履歴待ち、再試行、Snapshot生成を含め、FIFO追加後のDB保存待ちは含めない。
- `analysis_attempt_count`は観測用の実解析開始直前に加算する。履歴確認だけの処理、事前分析で破棄する処理、DB再送は含めない。
- M5バーが変わったら通貨ごとの計測起点・回数をリセットする。再起動前のカウンターを引き継がない。
- TESTER保存ゲートが開いた後は観測用解析回数を別管理し、準備用解析を混在させない。同じ候補M5の初検出時点が保持されていれば、その起点からの取得時間を記録する。
- 品質値は分析結果と一緒にSnapshotへ固定する。保存成功まで同じ値を維持し、DB再送ごとに再計測しない。

## 9. 重複・トランザクション・検証

### 9.1 自然キー

既存の自然キーを維持する。

```text
source_mode + source_server + symbol_name
+ anchor_time_frame + anchor_bar_time + capture_phase
+ analysis_version + analysis_input_hash
```

`run_id`は自然キーへ含めない。基準足と分析ProfileでH1／M5を区別できるが、初期版の運用ではDB自体も分離する。

同じキーではfirst-write winsを適用する。同一hashでも異なるhashでも、最初の親・時間足別・品質行を保持する。既存観測に品質行がない場合も、後日の計測値で補完しない。実行条件やテスターモデルの異なる比較は別DBで行う。

異なるRunが同じキーを保存済みの場合は、現行Controllerと同じWriter競合として扱う。PASSIVE／ERRを表示して新規収集・保存を停止し、先行Runの値へ上書きしない。再起動や新規Run作成だけでは重複を回避できないため、同じ期間を再収集する場合は新しいDBを使用する。

### 9.2 保存単位

新規観測は、親1行・時間足別7行・品質1行の計9行を1トランザクションで保存する。いずれかの失敗時はROLLBACKし、一部だけを残さない。Runは従来どおり事前に準備するため、Runだけがある状態は発生し得る。

28通貨全体を1トランザクションにはしない。28通貨成功時の行数は、観測28行・時間足別196行・品質28行となる。

### 9.3 保存前の検証

- 基準足がM5、子件数が7で親の`time_frame_count`と一致すること。
- 4.1の時間足集合・順序と完全一致し、足種・順序に重複がないこと。
- アンカーはM5の1行だけであること。
- 価格・Spread・pip size・日時・真偽値など、既存の保存検証を満たすこと。
- サーバー時刻・JST変換・表示文字列が一致すること。
- 品質行が1行で、各値がNULLまたは規定の範囲であること。
- RunとSnapshotの実行元・分析Profileが一致すること。
- 解析前後とSnapshot確定時に同じ対象M5であること。後続M5のデータを前のM5へ保存しないこと。

DBの一意制約・外部キーは既存の親子構造を利用し、足数・順序・アンカーの完全性は保存サービスでも確認する。品質テーブルの主キーで1対1を保証する。

## 10. Profile・バージョン・Hash

計算パラメーターと観測契約を区別する。既存`ZigZagElliotAnalysisProfile`のH1用getterをM5へ直接置換しない。

| 項目 | 用途 |
|---|---|
| `input_text`／`input_hash` | DB名、Common使用、Timer・DB再試行、保存開始時刻、Queue容量、解決済み28通貨などの運用入力 |
| `analysis_version` | 共通Elliott計算の世代。作成時ソースは`ELLIOT_MN1_V6` |
| `analysis_input_text`／`analysis_input_hash` | 共通計算パラメーターと、M5基準・7足順序・取得方式などの観測Profile |
| `snapshot_hash` | 取得した市場・分析値の同一性比較 |
| `program_version`／`strategy_version`／`schema_version` | プログラム、収集契約、Run保存形式の識別 |

M5のCanonical Textには、実際の基準足・分析開始足・足数・足順序、固定計算パラメーター、観測方式、同一気配からSpreadを取得する規則を明示する。H1のCanonical Textを複製してH1設定を残したまま、後ろにM5設定を重複追加する方式は避ける。

`analysis_input_hash`は既存同様SHA-256で生成し、M5の識別子を含めてH1と区別する。Snapshot Hashは既存の非暗号学的な内容比較方式を利用し、M5専用の形式識別子と7足の固定順序を使用する。

v1.03はM5 Snapshot Hash形式を`M5_OBSERVATION_V2`とし、各時間足の既存スカラーの後に`previousMotiveSubElliotIndex`を追加する。Elliott計算・分析Profile・Runのschema_versionは変更しない。H1 Snapshot Hashの形式・値の構築順序は維持する。

取得品質5項目は`analysis_input_hash`と`snapshot_hash`へ含めない。同じ分析値でも実行環境・待ち時間・試行回数が変わるためである。品質行の整合は外部キー、同一トランザクション、Snapshot固定および保存テストで確認する。

H1の既存Canonical Text、Hash生成規則、保存されたHash値、Run識別値は変更しない。M5対応に伴ってH1の分析設定が変わったように見える変更を防ぐため、既存H1の文字列・Hash一致を回帰テストする。

## 11. 収集開始・境界・ウォームアップ

### 11.1 LIVEとTESTER

| 条件 | 開始時の扱い |
|---|---|
| LIVE | `OnTimer`で確認。起動時の進行中M5はbaselineとし、次の新規M5から保存 |
| TESTER・保存開始0 | `OnCalculate`で確認。通貨ごとに初回分析・Snapshot生成へ成功した現在M5から保存。全28通貨の開始同期ゲートなし |
| TESTER・保存開始>0 | 保存開始前は1時間間隔の準備・事前分析のみ。開始時刻以降、同じ候補M5で全28通貨が事前分析成功したら開始ゲートを開く |

保存開始時刻は取引サーバー時刻であり、JST入力とは扱わない。例えば開始`18:03`なら`18:00`は対象外で、`18:05`以降が最初の候補となる。

M5のTESTERで保存開始>0かつ`TimeCurrent() < observationTesterSaveStartTime`の間だけ、全28通貨を巡回する準備処理を初回は即時、以後は最短3,600秒間隔にする。間隔は模擬サーバー時刻基準であり、毎tick・毎M5の全通貨巡回を省く。事前の実解析自体も初回成功まで1時間間隔とし、一度成功した通貨は保存開始まで実解析を繰り返さない。準備用の結果は保存せず、FIFO・Gap・DB Runを生成しない。

`TimeCurrent() >= observationTesterSaveStartTime`となったtickでは、前回準備から1時間未満でも待機を解除し、同じtickで通常の開始判定へ進む。開始時刻以上の候補は、同じ候補M5で改めて全28通貨を事前解析する。この段階は各M5で最大1回の既存の再試行規則を維持する。全通貨巡回の1時間間引きはM5の保存開始前だけに適用し、H1、LIVE、保存開始0、および保存開始時刻以降の全通貨巡回周期は変更しない。各通貨の履歴確認・不足取得には4.2節の共通間隔を適用する。新しいinputは追加せず、観測範囲・分析Profile・DB形式も変更しない。

同じM5の28通貨がそろったら、その実行内の第2 passで観測用に再分析して通常保存へ移る。事前分析の結果をそのまま観測へ転用しない。ゲートは収集開始をそろえる仕組みであり、28件の同時取得・一括COMMIT・全件保存成功を保証するものではない。

### 11.2 通常収集と欠損

1. 各通貨の新しいM5を検出し、対象バーと計測起点を保持する。
2. 7系列の同期・必要本数を確認する。
3. 解析前の基準M5を再確認し、気配を採用して全7足を分析する。
4. 解析後も同じM5であることを確認し、分析結果と品質情報を固定する。
5. SnapshotをFIFOへ追加し、以後は再分析せず保存を再試行する。

LIVEのpendingおよびTESTER初回Snapshot生成成功後の失敗は、同じM5内で再試行する。DBへの初回保存成功を待つ条件ではなく、初回SnapshotがFIFOで保存待ちでも通常の解析再試行へ移る。TESTER保存開始0で初回Snapshot生成へ成功する前の準備・解析失敗、および保存開始>0で開始時刻に到達した後の事前分析失敗は、既存同様、次のM5で再評価する。保存開始前だけは11.1節の1時間間隔を適用する。

次のM5までに取得できなかった通常観測は欠損とする。中間の欠損数は実在バーから判定し、週末のようにバーがない時間を機械的に欠損へ数えない。起動baseline・保存開始前・初回準備中は通常Gapと分け、長期データの完全性確認ではパネルのGapだけに依存しない。

## 12. FIFO・負荷・状態表示

生成済みSnapshotは中央FIFOで順序を維持する。DB保存失敗では先頭を削除せずDrainを止め、設定間隔で同じRunへの接続・保存を再試行する。

Queueが満杯なら新規Snapshot生成を止め、対象M5をpendingのまま維持する。次M5まで空きがなければ欠損になる。FIFOはメモリ上だけにあり、インジケーター・端末の終了時に未保存分は失われる。初期版ではディスク退避を追加しない。

| 指標 | 規模・扱い |
|---|---|
| 1回の28通貨収集 | 親28行＋時間足別196行＋品質28行 |
| 1時間の観測回数 | 12回（各M5バーが存在し、全回成功する場合） |
| H1比の親観測行数 | 12倍 |
| H1比の時間足別行数 | 16.8倍（12×7÷5）。品質行は別途追加 |
| Queue 672件 | 28通貨×24回＝M5では約2時間分。H1の24時間分とは異なる |
| 性能確認 | 短期実測で28通貨の処理時間・取得遅れ・DB容量・Queue滞留を確認 |

LIVEの処理性能は未計測であり、CPU負荷が単純に12倍または16.8倍になるとは断定しない。LIVEで次の5分境界までに収集を完了できることを最低確認条件とし、14.4節のテスター実所要時間とは分けて評価する。根拠のない上位足キャッシュや取得遅延によるデータ除外は導入しない。

状態パネルは、準備／検出／解析／保存の通貨数、DB接続、Writer状態、Queue件数・容量、Gap、通貨別の待機・再試行・エラーを表示する。M5詳細は4列×7行で、各通貨の下段に直近取得の`HH:MM A350ms C3.0s x2`を表示する。Aは解析時間、Cは初検出からSnapshot確定までの時間、xは観測解析回数であり、数値は表示例である。

これらとは別に、直近の履歴確認が完了した通貨数を`履歴準備 n/28`、全通貨完了時は`履歴準備完了 28/28`と表示する。既存のReadyは「観測準備」として初回分析や事前分析など収集側の進捗を表し、履歴準備の件数へ置き換えない。履歴が28/28でも分析待ち・開始日時待ち・DB待ちになる場合がある。通貨別ツールチップにも`履歴準備: OK / WAIT`と既存の状態メッセージを表示する。

品質のHH:MMは対象M5のサーバー時刻。日時・正確なms値・気配時刻はツールチップに表示し、未取得は`-`、有効な0は`0ms`とする。直近成功値は次の取得成功まで残し、DB保存済みであることは意味しない。上段の集約時刻は従来同様JSTと明記する。28通貨が完全に同一tickで取得されたと読める表示は行わない。H1・M5とも履歴準備の表示行を追加し、通貨詳細の配置と既存オブジェクト名を維持する。

インジケーターのテスターでは`OnDeinit`やグローバルオブジェクトのデストラクターが実行されないため、終了処理からのサマリー出力を完了判定に使用しない。[MQL5：インジケーターのテスト](https://www.mql5.com/en/book/applications/indicators_make/indicators_test)

代わりにM5のTESTERだけ、収集処理`execute()`の保存処理後、および収集停止・実行元確認待ちで処理を戻す経路から`M5_TESTER_PROGRESS`を出力する。これらの経路で初回・保存件数を含む状態変化・時刻後退を確認すると出力し、不変なら模擬サーバー時刻で3,600秒以上経過した巡回で出力する。日時表示の変化だけでは状態変化とみなさず、H1・LIVEのログ動作は変更しない。

保存開始前の準備処理の間引きは維持する。この間に実行元確認待ちが解消した場合、復旧状態のログは次の1時間巡回まで遅れることがある。保存開始時刻に達すると間引きを解除するため、このログの遅れによって保存開始を遅らせることはない。

進捗には`phase`、`saveStart`、`serverTime`、`lastM5`、`gateOpened`、`ready`、`dbReady`、`saved`、`queued`、`gaps`、`message`を記録する。

| `phase` | その時点の状態 |
|---|---|
| `STOPPED` | 異常で収集停止。テスターの実行終了を意味しない |
| `SOURCE_WAIT` | 実行元情報の確認待ち |
| `WARMUP` | 指定した保存開始時刻より前の準備段階 |
| `WAIT_GATE` | 保存開始時刻以降、全28通貨の事前解析・開始ゲート待ち |
| `DB_WAIT` | 保存先DBの準備・再接続待ち |
| `COLLECTING` | 通常収集段階。全件の保存完了を保証する表示ではない |

最後の進捗行も、出力した時点の状態を示すだけで終了確定の通知ではない。終了・収集結果の確認にはMT5自体の終了ログ、最後の進捗、および対象期間のDB監査を併用する。保存0件、保存待ち残数、ゲート未開放なども確認し、テスターの終了やGap 0だけを収集完了と扱わない。

### 12.1 DB容量の見積もり前提

初期の領域計画は、**28通貨・2年間でDB本体約20～28GiB、中心値約24GiB**とする。これはM5収集実装後の実測値ではなく、現行H1データを使った模擬DBと余裕を基にした概算であり、上限保証ではない。

| 前提 | 値・範囲 |
|---|---|
| 通貨数 | 28通貨、すべて保存成功する前提 |
| 1稼働日のM5数 | 24時間×12本＝288本／通貨 |
| 1稼働日の観測数 | 28×288＝8,064件 |
| 期間換算 | 1週5日、1か月22日、3か月66日、6か月130日、1年260日、2年520稼働日 |
| 1観測の内容 | 親1行＋時間足別7行＋品質1行、および対応する索引・ページ内余白 |
| 容量単価 | 1観測あたり5～7KiB。中心値6KiB |
| 見積もり対象 | Observation DB本体。通常規模のRun・スキーマの固定費は端数として扱う |
| 対象外 | WAL／SHM、バックアップ、保守作業領域、MT5の価格・tick履歴、ログ、他DB、将来のEpisode・成績テーブル |

1KiB＝1,024bytes、1GiB＝1,073,741,824bytesとする。ストレージで使われる1GB＝1,000,000,000bytesとは区別し、20～28GiBは約21～30GBに相当する。

稼働日は「各通貨に24時間分のM5がある日」として容量計算用に置いた値であり、暦上の営業日数や実収録本数を断定するものではない。休日・短縮日・休場・欠損があれば実行数は変わる。欠損を見込んで必要容量を小さくしない。月・四半期の換算は独立した概算なので、22日×12か月と年260日を同一とは扱わない。

```text
観測件数 N = 28通貨 × 288本/稼働日 × 稼働日数
時間足別行数 = 7 × N
品質行数 = N
DB本体 bytes ≒ N × 5,120～7,168bytes（中心6,144bytes）
```

|---|---:|---:|---:|
| 1日 | 1 | 8,064 | 約0.038～0.054 |
| 1週 | 5 | 40,320 | 約0.19～0.27 |
| 1か月 | 22 | 177,408 | 約0.85～1.18 |
| 3か月 | 66 | 532,224 | 約2.54～3.55 |
| 6か月 | 130 | 1,048,320 | 約5～7 |

### 12.3 見積もりの根拠と限界（2026-09-10確認）

既存DBは読み取り専用で照会し、模擬計算はSQLiteのメモリDBだけで行った。運用DBへのINSERT、migration、checkpoint、VACUUM、ファイルコピーは実施していない。

**既存の研究DBそのものの実測：** Common/Filesの`mstng-zigzag-elliot-h1-study-2024-2025-r1.sqlite`は、DB本体1,087,754,240bytes（約1.013GiB）、親350,713行、子1,753,565行だった。ただし時間足別テーブルは旧74列で、現在の最新ポイント詳細を含む88列ではない。実収録範囲も2024-01-02 01:00から2026-01-06 23:00までのサーバー時刻であり、ファイル名だけから厳密な2年間の単価にはしない。このDB全体へ一律に12倍・16.8倍を掛けた値は採用しない。

**現行形式での模擬容量測定：** `mstng-zigzag-elliot-alert.sqlite`から、5時間足すべての最新F列が記録済みである直近4,000観測・20,000時間足行を読み取った。対象は28通貨、2026-09-02 10:00から2026-09-10 08:00までのサーバー時刻だった。以下の条件でM5用の行構成をメモリ内に作り、`page_count × page_size`を測定した。

- Python側SQLite 3.50.4、ページサイズ4,096bytes。MT5組み込みSQLiteでの実収集結果ではない。
- 現行の親20列・子88列と、3つの共通テーブルの明示索引14本・UNIQUE由来の索引3本を利用。採用した観測が参照するRunも格納。
- 元の5時間足に、H1行の値を代用したM15・M5行を追加し、足種・順序・アンカーを変更。**M15・M5の価格・波動を実分析した値ではない。**

| 模擬観測件数 | 子／品質行数 | ページ占有bytes（固定費込み） | 固定費を除く1観測単価 |
|---:|---|---:|---:|
| 1,000 | 7,000／1,000 | 4,460,544 | 4,337.664bytes（約4.24KiB） |
| 4,000 | 28,000／4,000 | 17,432,576 | 4,327.424bytes（約4.23KiB） |

### 12.4 WAL・バックアップ・作業用領域

本体容量と、そのDBを運用するために必要な領域は分ける。

```text
通常の必要領域 ≒ DB本体B + 同じディスクに置くバックアップ容量 + WAL/SHM + 安全余裕
```

WALは未checkpointの変更を保持する別ファイルであり、チェックポイントの目安サイズを容量上限とは扱わない。長時間の読み取りなどで大きくなる場合があるため、本体とWALを別々に監視する。バックアップは整合性を確保できる方法を別途使用し、稼働中の`.sqlite`だけを単純コピーしてよいという意味ではない。[SQLite WAL](https://www.sqlite.org/wal.html)

| 2年間を保存する場合の領域計画 | 初期目安 |
|---|---|
| DB本体だけ | 約20～28GiB |
| 本体＋同容量のバックアップ1本＋通常の運用余裕 | この収集用に約64GiBを確保する案。本体28＋バックアップ28で56GiB、残り約8GiBをWAL等の仮の余裕とする |
| 上記に加え、同じ領域で通常のVACUUMを行う計画 | 約128GiBを確保する案。本体28＋バックアップ28＋追加作業領域最大約56で112GiB、それ以外に余裕を置く |

64／128GiBは他のMT5データを含まない容量予算であり、必ず収まる上限ではない。WAL、他DB、価格履歴、バックアップ世代数が増えれば追加領域が必要となる。作業用一時ファイルを別ボリュームへ配置する場合は、その空き容量も別途確認する。

通常のVACUUMは、元DBとは別に最大で本体約2倍の追加空き容量を必要とする。本体を含めた約2倍ではない。これはVACUUM用一時DBと書き戻し時のjournal／WALを考慮する値なので、同じ作業WALを重複加算しない。VACUUMの実施自体は本書の自動処理に含めず、必要時に別途判断する。[SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)

### 12.5 実装後の見積もり更新

M5実装後、専用の短期検証DBで通常の28通貨収集を行い、数日分以上の実データから再見積もりする。1回の起動直後や、NULL中心の未完成データだけを測定対象にしない。

1. 親・子・品質の件数、7足の完全性、Profile数と期間を確認する。
2. 本体bytes、ページサイズ、ページ数、未使用ページ数、WAL／SHM bytesを別々に記録する。
3. 完了済み収集DBなど、WAL状態を確認できる条件で、観測件数の増加に対する本体ページ増加を測る。容量測定だけのために運用DBへcheckpointやVACUUMを実行しない。
4. 索引を含む1観測単価を求め、`予定観測件数 × 実測単価`で本体を更新する。ページ単価に含まれる余白を二重計上せず、追加の計画余裕は別記する。
5. 実測が5～7KiBを超える場合は予算を上方修正し、WAL・バックアップ・作業領域も連動して見直す。

今回使用したSQLiteには`dbstat`がなく、運用DBの親・子・索引別ページ内訳は直接取得していない。対応環境で内訳を取得できる場合は利用してよいが、索引や解放済みページを含むDB全体のサイズと混同しない。古いDBやAlert混在DBの全サイズを、Observation件数だけで割ってM5単価とする方法は避ける。
